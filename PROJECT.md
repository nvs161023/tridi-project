# TriDi — сводка по проекту

Единый обзор сервиса: что за продукт, из каких частей он состоит, какие функции и блоки уже
реализованы, где что лежит и что ещё предстоит сделать. Документ описывает состояние
репозитория на момент последнего коммита.

- **Продукт:** онлайн-курсы по 3D-печати. Базовый курс — бесплатно. Платные уровни «Уверенный» и
  «Инженер 3D-печати», продвинутый курс и конструктор 3D-моделей — по подписке. Внутри: уроки с
  блоками, тесты модулей с пояснениями, личный кабинет с прогрессом, юридический раздел по 152-ФЗ.
- **Домен:** https://tridi-print.ru
- **Владелец (он же оператор персональных данных):** самозанятый Накоряков Вадим Сергеевич,
  ИНН 531603515195 (НПД). Контакты для обращений — nvs16@ya.ru.
- **Стек:** Next.js 15.5.25 (App Router, Turbopack), React 19, TypeScript 5, Tailwind CSS 4,
  Supabase (@supabase/ssr 0.12.7 + supabase-js 2.116, self-hosted на VPS в РФ),
  three.js / @react-three (в зависимостях), хостинг приложения — Amvera Cloud (Москва).
- **Архитектурный принцип:** данные курсов и юридические тексты лежат отдельно от отображения;
  страницы — серверные компоненты, клиентского Supabase в браузере нет (авторизация идёт
  через Server Actions), доступ к платному контенту решается только на сервере.

трогает — им сессия не нужна.

## 3. Функции по блокам

### 3.1 Регистрация и подтверждение email

Полный цикл: **регистрация → письмо → переход по ссылке → сессия → доступ**.

1. `signUpAction` (`app/actions/auth.ts`) создаёт аккаунт серверным клиентом Supabase и передаёт
   `emailRedirectTo` — адрес `/auth/confirm` на нашем домене плюс `next`, куда вернуть человека.
   Адрес строит `lib/site-url.ts`: `NEXT_PUBLIC_SITE_URL` → (в разработке) хост из заголовка
   запроса → боевой домен `https://tridi-print.ru`. Заголовок `Host` учитывается только вне
   продакшена, чтобы адрес в письме нельзя было подменить.
2. Если Supabase вернул сессию (подтверждение в проекте выключено) — сразу вход; если нет —
   редирект на `/auth/verify-email?next=…` с сообщением «мы отправили письмо».
3. Ссылку из письма открывает страница `app/auth/confirm/page.tsx`. Она намеренно **ничего не
   подтверждает сама**: такие адреса открывают и почтовые сервисы (Mail.ru и подобные), которые
   проверяют ссылки в письмах, — при подтверждении по GET одноразовый токен сгорал до того, как
   письмо прочитает человек. Поэтому токен уходит в Supabase только после нажатия кнопки
   «Подтвердить email» (`supabase.auth.verifyOtp`), а сессию записывает браузерный клиент
   `lib/supabase/client.ts` (он же записывает восстановительную сессию при сбросе пароля, см. 3.2).
   Поддерживаются **два
   формата** ссылок, потому что шаблоны писем у Supabase бывают разные:

   | Формат ссылки | Как обрабатывается |
   |---|---|
   | `?token_hash=…&type=…` (рекомендуемый) | страница `/auth/confirm` показывает кнопку, `supabase.auth.verifyOtp()` вызывается по клику |
   | `#access_token=…` (шаблон Supabase по умолчанию) | фрагмент адреса не уходит на сервер, поэтому его разбирает клиентский `components/EmailLinkHandler.tsx` и передаёт токены в Server Action `app/actions/confirm-session.ts` (`setSession`) |

   Если в адресе есть `error`/`error_code` или нет `token_hash`/`type`, кнопку показывать нечего:
   страница сразу уводит на `/auth/verify-email?status=error`. Ссылка с `?code=…` (поток PKCE)
   больше не поддерживается — такой адрес тоже попадёт на страницу со статусом «ссылка не
   сработала», откуда можно запросить новое письмо. `next` санитизируется (`resolveAfterAuthPath`,
   только внутренние пути), а `type` и сам токен проверяет Supabase.
4. Подтверждение выполняется в браузере, потому что сессия пишется в cookies: в Server Component
   запись cookies запрещена, а `lib/supabase/server.ts` ошибки записи глушит — страница молча
   не сохранила бы сессию. Плата за это — клиент Supabase (~70 КБ) в бандле `/auth/confirm`;
   при открытии адреса почтовым сканером без JavaScript не происходит ничего.
5. `/auth/verify-email` не только показывает статус: там форма повторной отправки
   (`resendVerificationAction`, письмо уходит с тем же `emailRedirectTo`). Ответ нейтральный
   («если адрес зарегистрирован и не подтверждён — письмо отправлено»), чтобы форма не стала
   инструментом проверки чужих адресов; лимит отправок обрабатывается отдельным сообщением.
6. Пока почта не подтверждена, middleware не пускает в `/course/*` и `/dashboard` — человек
   попадает на `/auth/verify-email?next=<куда шёл>`. Страница подтверждения и `/auth/confirm`
   открыты и вошедшим: иначе получилась бы петля (middleware → кабинет → middleware), а токен
   из письма остался бы неиспользованным.

**Настройка на стороне владельца (self-hosted Supabase):** Site URL и Redirect URLs
(`https://tridi-print.ru/**`), шаблон письма **Confirm signup** со ссылкой
`{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup` и шаблон **Reset password**
со ссылкой `{{ .SiteURL }}/auth/reset-password?token_hash={{ .TokenHash }}&type=recovery`;
на хостинге — `NEXT_PUBLIC_SITE_URL`. Оба текста писем лежат в репозитории —
`public/templates/confirmation.html` и `public/templates/recovery.html`: их содержимое нужно
целиком вставить в соответствующие шаблоны Supabase (сам Supabase в репозиторий не входит).
Подробнее — README, разделы «Подтверждение email» и «Сброс пароля».

### 3.2 Вход, выход и восстановление доступа

- Вход — `signInAction`: email и пароль, ошибки Supabase переводятся на русский
  (`translateSignInError`): «Email ещё не подтверждён…» и лимит попыток подсказывают, что делать;
  всё остальное сводится к «Неверный email или пароль», чтобы не подсказывать, существует ли
  аккаунт. При успехе сервер сам записывает cookies сессии и уводит на `next` (или в кабинет).
- Выход — форма прямо в кабинете (`app/dashboard/page.tsx`): серверная функция вызывает
  `supabase.auth.signOut()` и делает `redirect("/")`. Отдельного action-файла для выхода нет.
- Вошедшему, но не подтвердившему почту пользователю закрытые разделы недоступны, а страница
  подтверждения предлагает отправить письмо снова.
- Сброс пароля: форма `/auth/forgot-password` отправляет письмо через `resetPasswordAction`, ответ
  всегда нейтральный («если аккаунт существует…») — по форме нельзя проверять чужие адреса. Ссылка из
  письма ведёт на `/auth/reset-password`, и подтверждает её **кнопка** (`verifyOtp` с
  `type=recovery`): только после этого на той же странице открывается форма нового пароля
  (`updateUser`). Так письмо не «сжигает» почтовый сканер — та же защита, что у подтверждения email.
  Обе операции делает браузерный клиент (`lib/supabase/client.ts`): восстановительная сессия ложится
  в cookies, а Server Component писать cookies не может. Адрес `/auth/reset-password` открыт и
  вошедшим (`AUTH_PAGES_FOR_SIGNED_IN` в `lib/supabase/middleware.ts`): после подтверждения ссылки
  сессия уже есть, и без этого исключения перезагрузка страницы или повторное открытие ссылки из
  письма уводили бы человека в `/dashboard`, а форма смены пароля пропадала бы.
- Ссылка сброса может не сработать (устарела, уже использована, Supabase сообщил `error`/`error_code`
  или в адресе нет `token_hash`): тогда страница показывает «ссылка не сработала» и предлагает
  запросить новое письмо. Ошибка при самом подтверждении уводит на
  `/auth/login?error=reset_link_invalid`; сообщения по этому параметру на входе пока нет — он
  зарезервирован под подсказку.

### 3.3 Доступ и подписка

Доступ решается в четырёх слоях, чтобы платный контент нельзя было получить в обход:

1. **Аккаунт** — есть ли вход (`lib/current-user.ts`).
2. **Подписка** — `subscriptions.status`: `active`, либо `trial` с `trial_ends_at` в будущем.
   Эту проверку делают страницы продвинутого курса (`canAccessProCourse` в `lib/basic-course.ts`
   и одноимённая локальная функция на странице урока/теста).
3. **Закрытый контент** — без подписки отдаются только первые **2 блока** урока
   (`PREVIEW_BLOCKS` в `app/course/pro/[moduleId]/[lessonId]/page.tsx`), дальше — замок со ссылкой
   на тарифы. Названия уроков и программа видны полностью: это осознанное решение — человек
   понимает, что покупает, но контента не получает.
4. **Прогрессия** — следующий модуль продвинутого курса открывается только после сданного теста
   предыдущего (`lib/module-test-progress.ts`).
5. **База** — `supabase/pro_course_access.sql` и `supabase/grants_and_policies.sql` (RLS-политики
   и гранты): анонимный доступ закрыт, строки прогресса видны только владельцу.

Тарифы: Free — 0 ₽ (базовый курс, тесты модулей, конструктор в ограниченном режиме),
Maker — 490 ₽/мес (бесконечные скачивания моделей, коммерческая лицензия, AI-диагностика),
Pro — 1 490 ₽/мес (Maker + продвинутый курс и его тесты, пакетная генерация, API, ранний доступ).
Состав тарифов и FAQ — в `app/subscription/page.tsx`; цена Pro берётся из `data/courses.json`
(`pro.price`) — того же файла, что использует страница урока продвинутого курса, чтобы цена в
замке и на витрине не разошлась. Цены продублированы в публичной оферте (`app/legal/offer`).
Кнопка оплаты (`app/subscription/PlanButton.tsx`) пока показывает «оплата подключается»:
платёжный провайдер не подключён, а порядок оплаты, чеки НПД и возврат уже описаны в оферте.
Функции «конструктор» и «AI-диагностика» из тарифов ещё не реализованы — см. раздел 12.

### 3.4 Базовый курс

- В `data/lessons.json` — **2 модуля, 8 уроков, 295 блоков**: оба модуля написаны целиком. Модуль 1
  «Основы 3D-печати» — уроки 1–4 и тест модуля (10 вопросов и 30 пояснений). Модуль 2 «Печать и
  первый результат» — четыре урока: 5 «Первый слой: физика адгезии» (37 блоков), 6 «Скорость,
  температура и поток» (38 блоков), 7 «Диагностика: 15 проблем и их решения» (42 блока) и 8 «Первый
  проект» (33 блока, 15 минут) — финал базового курса: один проект целиком, от выбора детали и
  ориентации с поддержками до печати с контрольными взглядами, постобработки и замеров, плюс
  чек-лист «курс пройден». Уроки 1–7 идут по 20 минут, и все про физику процесса, а не про перечень
  настроек: урок 7 — справочник из 15 проблем по схеме «как выглядит — причина — что делать — чем
  проверить», плюс порядок разбора сразу нескольких дефектов, шпаргалка быстрого обхода, протокол
  «одна ручка за раз» и журнал печати.
  Тест модуля 2 написан — 10 вопросов по урокам 5–8 и 30 пояснений, так что проверка знаний закрыта
  целиком по обоим модулям: 2 теста, 20 вопросов и 60 пояснений. Визуальные блоки уроков ждут файлов

### 3.6 Тесты модулей

- 10 вопросов на модуль, 3 варианта ответа, **3 пояснения** к каждому вопросу — к правильному
  ответу и к каждому неправильному, чтобы разбор был осмысленным.
- Базовый курс закрыт целиком: тест есть у каждого модуля — **2 теста, 20 вопросов и 60 пояснений**.
  Вопросы модуля 2 идут по урокам 5–8 со схемой 3 + 3 + 3 + 1: адгезия и первый слой, скорость с
  температурой и потоком, диагностика дефектов и один вопрос про первый проект.
- Уровень «Уверенный»: тесты всех трёх модулей написаны — **3 теста, 30 вопросов и 90 пояснений** по
  урокам C1–C12. Схема модуля 1 — 3 + 2 + 3 + 2 (воздух и иерархия защиты, вентиляция, пожар,
  химия и отходы), схема модуля 2 — 3 + 2 + 2 + 3 (поддержки и зазоры по Z, модификаторы и
  переменная высота слоя, разрез с соединениями и допусками, поверхность: шов, ironing,
  округлость и текстура), схема модуля 3 — 3 + 2 + 3 + 2 (калибровка, заполнение и мосты, старт
  G-кода и правки на лету, удалённый доступ и автопауза AI). Как только вопросы появились,
  включается и гейт: первый урок следующего модуля
  закрыт, а на последнем уроке модуля карточка «Проверь себя» держит продолжение заблокированным.
  У последнего модуля уровня «следующего» модуля нет, поэтому сдача теста модуля 3 открывает на C12
  поздравление «Курс пройден!» и кнопку «Перейти в конструктор», а гейт на C9 держит по-прежнему
  тест модуля 2 — третий тест его не снимает.
- **Гейт держит только первый урок модуля.** Тест предыдущего модуля закрывает ровно тот урок, с
  которого начинается следующий модуль: у «Уверенного» это C5 (тест модуля 1) и C9 (тест модуля 2), у
  продвинутого курса — тот же признак «первый урок модуля» (`isModuleFirst`). Остальные уроки модуля
  подписчику открыты, и экрана «Модуль закрыт» на них быть не должно: проверено вживую на C6 (второй
  урок модуля 2), так же проверяются C7 и следующие. Это правило платформы, а не дефект урока —
  переоткрывать его на каждом уроке не нужно.
- Пороги: сдано с **5** правильных, **8 и больше** — «отлично» (`MODULE_TEST_PASS_FROM`,
  `MODULE_TEST_EXCELLENT_FROM` в `lib/module-test.ts`). Попытки не ограничены.
- **Сохраняется только сданная попытка** (`app/actions/complete-module-test.ts`): наличие строки
  означает «модуль сдан», по ней открывается следующий модуль. Провал не пишется — иначе модуль
  открылся бы сам.
- Компонент `components/course/ModuleTest.tsx` — клиентский: по одному вопросу, сразу пояснение,
  в финале — оценка и разбор; после сдачи результат уходит на сервер и страница обновляется.
- Тест открывается **слайдом** поверх урока (`components/course/TestOverlay.tsx`): затемнение,
  `role="dialog"` + `aria-modal`, закрытие по Escape и клику по фону, возврат фокуса на кнопку.
  Пока слайд открыт, страница под ним не прокручивается; после сдачи вызывается `router.refresh()`,
  и заблокированная кнопка продолжения разблокируется без ручной перезагрузки.
- Карточку на уроке рисует `components/course/ModuleTestGate.tsx`: при несданном тесте — кнопка
  «Пройти тест» и **заблокированное** продолжение с подписью «Сначала сдай тест» (дальше не пускаем),
  при сданном — активное «Продолжить курс» и «Пройти тест ещё раз». Цвета курса — в
  `components/course/module-test-theme.ts` (общий модуль без `"use client"`, поэтому его читают и
  серверные, и клиентские компоненты).
- `ModuleTest` работает в двух режимах: `layout="page"` (страница `/course/check/<код>`) и
  `layout="overlay"` (слайд; внутри — кнопка «Закрыть» вместо ссылки «к урокам модуля»).
- Если результаты прочитать не удалось (нет сети или таблицы), считается, что тест сдан:
  запереть ученика из-за сбоя чтения хуже, чем показать урок.

Правила визуализаций (проверяются перед коммитом каждого модуля):

- один блок — один компонент — один файл, повторов между уроками нет;
- кадр всегда `viewBox="0 0 320 180"`, подписи не выходят за него — замер живой вёрстки, а не на глаз;
- **шкала шрифтов**: база — 10 px, это заголовки кадров и подписи основных элементов;
  плотные кадры продвинутого курса (таблица параметров, диптих, триптих, выноски к размерам)
  набираются подписями 7,5–9 px — на телефоне это 6,9–8,3 px, поэтому такой кадр обязан
  дублировать сюжет текстом урока: списки `content` и `items` называют те же элементы словами,
  и картинка остаётся подписью к тексту, а не единственным носителем смысла;
- минимум подписи — 10 px по кадру: на телефоне кадр сжимается до 294 px, то есть ≈9,2 px на экране;
- **исключений из минимума больше нет**: два исключения были у кадров прежней программы
  (`basic-10-image-0` — сетка 2×5 плиток со шрифтом 8 px, `basic-11-image-1` — буква-логотип 9,5 px),
  но эти файлы удалены; в новом контенте держим общий минимум 10 px.
- **блок `animation` обязан двигаться**: кадр с типом `animation` содержит `@keyframes` и блок
  `@media (prefers-reduced-motion: reduce)` с финальным состоянием — статичная картинка в блоке
  «анимация» читается как ошибка. Проверка живой вёрстки смотрит `animationName` у элементов кадра.
- **счётчик в кадре** — это окно `clipPath`: числа (или значения) стоят в ряд и едут под неподвижным
  окном, поэтому видно только текущее. Клип висит на неподвижной обёртке, а едет внутренняя группа:
  `clip-path` на самом движущемся элементе уезжает вместе с ним и уводит окно из кадра.
- **подписи в `pro-J-J1-image-0` и `pro-J-J2-image-0` разведены**: строки правил стояли парами впритык
  (зазор 3,5 px), при перерисовке кадров под анимацию шаг строк стал 13,5 px, просвет 5 px —
  предупреждений замерщика по урокам J1 и J2 больше нет.
- **ценник в `pro-T-тизер-T-тизер1-image-0` без чисел**: урок называет товары, а не цены, поэтому у
  каждой позиции витрины стоит знак рубля и подпись словами из списка «Что продавать». Число в кадре
  появилось бы из ниоткуда — это ровно то, чего правила визуализаций не допускают.
- **подписи ценников набраны 7,5 px** — кадр плотный (шесть позиций и шесть ценников в одном кадре),
  поэтому он опирается на текст урока: подписи на ценниках — это те же шесть пунктов списка
  «Что продавать», и на телефоне кадр читается вместе с ним, а не вместо него.
- **купол датчика в `pro-C-пож-C-пож1-image-0` уводили с подписи принтера**: на первом скриншоте
  символ датчика лёг ровно на слова «источник тепла 200–300 °C» и закрыл их. Датчик сдвинут к
  правой части стола, подпись принтера стала короткой («принтер» / «200–300 °C») и ушла влево, а
  слова «источник тепла» переехали в подпись кадра — те же слова есть в тексте урока
  («3D-принтер — источник тепла 200–300 °C»). Там же линия питания шла сквозь катушку на столе —
  кабель опущен ниже катушки. Замер после правки: подписи внутри кадра, наложений нет.
- **цены в подписи кадра — из врезки урока**: «датчик дыма — 1500–3000 ₽» стоит во врезке `tip`
  урока C-пож1, поэтому в кадре те же цифры; своих чисел визуализация не придумывает.
- **матрица 5×3 в `pro-C-пож-C-пож2-animation-0` дублируется списком урока**: подписи строк и

### 3.12 Уровень «Уверенный» (каркас)

Платный уровень между базовым курсом и «Инженером»: продолжение бесплатной части для тех, кто уже
печатает и хочет делать это безопасно и осознанно. Материалы уровня пишутся (см. раздел 12), а
инфраструктура готова целиком — уроки добавляются данными.

- Программа: `data/course-confident.json` — **3 модуля, 12 уроков** (коды C1…C12) и три теста
  модулей. Написаны все двенадцать уроков: четыре в модуле 1, четыре в модуле 2 и четыре в модуле 3 —
  C1 «Что летит в воздух:
  UFP, VOC и защита дыхания» (32 блока, 7 кадров визуализаций), C2 «Вентиляция и рабочее место»
  (31 блок, 6 кадров), C3 «Пожарная безопасность и аварийные сценарии» (30 блоков, 6 кадров),
  C4 «Химия, СИЗ и утилизация отходов» (32 блока, 6 кадров), C5 «Поддержки, которые отделяются
  сами» (35 блоков, 6 кадров), C6 «Модификаторы и переменная высота слоя» (35 блоков, 6 кадров),
  C7 «Модель больше стола: разрез, соединения, допуски» (35 блоков, 6 кадров), C8 «Идеальная
  поверхность: шов, ironing, округлость, рельеф» (35 блоков, 6 кадров), C9 «Продвинутая калибровка
  принтера» (35 блоков, 6 кадров), C10 «Заполнение и сложные геометрии» (35 блоков, 6 кадров),
  C11 «G-код: читать, писать, менять на лету» (35 блоков, 6 кадров) и C12 «Сеть, мониторинг и
  печать без присмотра» (35 блоков, 5 кадров) — последний урок модуля 3 и всего уровня.
  Пустых уроков в данных не осталось. Тесты всех трёх модулей
  написаны — 30 вопросов и 90 пояснений.
- Страницы: `app/course/confident/page.tsx` (программа уровня), `app/course/confident/[moduleId]/[lessonId]/page.tsx`
  (урок), `app/course/confident/[moduleId]/check/page.tsx` (тест модуля).
- Доступ: уроки и тесты уровней «Уверенный» и «Инженер» открывает одна подписка, поэтому проверка
  одна на всех — `lib/subscription.ts` (`hasActiveSubscription`). Без подписки страница урока отдаёт
  2 блока превью и замок, как и продвинутый курс.
- Прогресс: уроки пишутся с `course_type = "confident"` (номер урока 1…12), тесты модулей — с
  `"confident-test"` (номер модуля 1…3). Тип строки заведён в `lib/module-test.ts`, а значение
  `course_type` в базе разрешает `supabase/confident_course_access.sql` (применяется вручную).
- Разворот модулей в плоский список уроков и поиск модуля/урока — `lib/confident-course.ts`.
- Написанные уроки страницы показывают как обычно (блоки, прогресс, кнопка «Пройти урок»). Механика
  для материалов, которых ещё нет, осталась рабочей: в программе у урока встаёт «Готовится», в уроке —
  «Материал готовится», в тесте модуля — «Тест готовится», а гейт по тесту предыдущего модуля
  включается только тогда, когда тест написан (иначе человек упирался бы в несуществующую
  проверку). У «Уверенного» эти отметки теперь негде увидеть: 12 уроков и 3 теста написаны, и
  страницы отдают данные.
- Принцип уровня (правило от 04.10, действует с C2): «Уверенный» — про уверенное владение принтером,
  а не про инженерные расчёты; переписывать мануал к принтеру не наша работа. Объём урока —
  4 500–6 000 слов и 28–35 блоков, визуализаций 5–6 (для сравнения: средний базовый урок — 6 779 слов
  и 36,9 блока). Тема требует больше — пишем больше; хватает 4 500 — останавливаемся на 4 500. Знаки не
  считаем. Фокус уровня — ежедневная практика: поддержки и модификаторы (C5–C6), крупные модели и
  соединения (C7), поверхность и швы (C8), калибровка и сложные геометрии (C9–C10), G-код и макросы
  (C11), сеть и мониторинг (C12).
- Стиль уровня (правило от 04.10, действует с C3): подача — для человека, который печатает дома, а не
  для инженера. Предложение — не длиннее 12 слов, длинное разбивается на два-три. Абзац — 2–4
  предложения, между абзацами пустая строка. Один абзац — одна мысль. Бытовой пример идёт до теории
  («представь свечу» — потом про то, как горит пластик). Термин объясняется сразу, в том же абзаце, а
  ключевые термины и цифры выделяются **жирным**. Списки — короткие пункты на одну-две строки.
  Обращение — «ты». Сложные слова заменяются простыми: «делается» вместо «осуществляется», «через»
  вместо «посредством». Абзацы и жирный в тексте рисует `components/course/LessonBlocks.tsx`
  (`BlockText` и `inlineText`): пустая строка в данных — граница абзаца, `**термин**` — жирная вставка.
  C1 и C2 переписаны в новом стиле (метрики — в записи об итерации в разделе 13), правило действует на все написанные уроки уровня.
Медиаподпись — это одна фраза не длиннее 100 знаков: `BlockVisual` показывает первые 100 знаков
`content`, поэтому длинное описание кадра до читателя не дойдёт. Детали такого описания переносят в
соседний блок — так исправлен C3 (все шесть подписей сжаты до 49–76 знаков, а числа и шаги из
описаний ушли в тексты и списки рядом).
- Объём и стиль урока измеряются, а не оцениваются на глаз: `npm run stats:lesson`
  (`scripts/lesson-stats.mjs`) считает блоки, слова, знаки без пробелов, среднее слов на блок и
  разбивку по типам, а для урока «Уверенного» сверяет его с ориентиром 28–35 блоков / 4 500–6 000
  слов. Текст берётся из тех же полей, что читает страница урока (`content`, `items`, `steps`),
  заголовки блоков — метаданные и в счёт не идут. Стиль проверяет `npm run check:style`
  (`scripts/style-check.mjs`): предложение не длиннее 12 слов, абзац не длиннее 4 предложений; список
  `LEGACY_LESSONS` пуст — C1 и C2 переписаны, пропускать больше нечего.

Все блоки рисует `components/course/LessonBlocks.tsx`; незнакомый тип блока не ломает страницу —
он просто не отображается. Форма блока описана в `lib/types.ts` (`LessonBlock`).

| Тип блока | Что показывает | Поля данных |
|---|---|---|
| `text` | Абзац с заголовком | `title`, `content` |
| `list` | Маркированный список | `title?`, `items[]`, `visual_file?` |
| `steps` | Инструкция по шагам (нумерация, «шаг N») | `title?`, `steps[]` (строка или «заголовок + пояснение») |
| `tip` | «Совет» — акцентная врезка | `title`, `content` |
| `warning` | «Важно» — предупреждение | `title`, `content` |
| `analogy` | Аналогия — образное объяснение | `title`, `content` |
| `image` | Иллюстрация; пока заглушка с иконкой | `title`, `content` (описание), `visual_file`, `src?` |
| `animation` | Анимация/видео; пока заглушка | `title`, `content`, `visual_file` |
| `screenshot` | Скриншот интерфейса; пока заглушка | `title`, `content`, `visual_file` |
| `diagram` | Схема; пока заглушка | `title`, `content`, `visual_file` |
| `mini_check` | Мини-проверка в уроке (`components/course/MiniCheck.tsx`) | `questions[]` — вопрос, 4+ варианта, номер правильного, пояснения |

Визуализация привязана к типу блока не жёстко: если у блока `text`, `list` или `steps` есть
`visual_file`, карточка кадра встаёт рядом с содержимым, а подпись немедийного типа берётся у
иллюстрации (`BlockVisual`). Так список пунктов может идти вместе со схемой-обзором — в уроке C1 это
«Что выделяет каждый материал» и «СИЗ: что держать рядом», а в C2 шаги сборки фильтр-бокса идут со
схемой потока воздуха (`C2_airflow.png`). В базовом и продвинутом курсах `visual_file` есть только у
медийных блоков, поэтому их вид не меняется.

`screenshot` до модуля 2 «Уверенного» не использовался ни разу: кадры интерфейса слайсера появились в C5
(1 блок), C6 (2 блока), C7 (1 блок) и C8 (2 блока) — всего 6, а в C9 к ним добавились два кадра интерфейса
прошивки (консоль автоподбора PID и таблица резонансов), в C10 — два кадра слайсера (окно заполнения
и галочка Print Thin Walls), в C11 — два кадра интерфейса (окно стартового G-кода и окно постобработки),
в C12 — два кадра интерфейса (панель управления печатью и кадр камеры с рамкой обнаружения)
— 14 кадров у уровня. В базовом и продвинутом
курсах этот тип работает давно (интерфейс
принтера, `printer.cfg`, окно переписки в `pro-P-P5-screenshot-0`). Подпись кадра у медиаблока лежит в
том же поле `content`, что читает `BlockVisual` (первые 100 знаков идут в подпись, дальше — «…»), и её
проверяет `scripts/style-check.mjs` наравне с текстом блока любого другого типа.

`mini_check` — **инфраструктура «на будущее»**: в текущих данных обоих курсов такие блоки не
используются, проверка знаний живёт на страницах тестов модулей. Компонент оставлен рабочим,
если понадобится короткая проверка прямо в уроке.

Форма данных — `lib/types.ts`: `Course → modules[] → lessons[]` (`lesson_id`, `lesson_order`,
`lesson_title`, `duration`, `blocks[]`) плюс `module_test` у модуля. Тест модуля — та же форма, что

Правила, на которых держатся страницы:

- `lesson_order` — **сквозной** номер урока в курсе (1…8 и 1…109), а не внутри модуля; место урока

## 7. Server Actions (серверные функции)

Все лежат в `app/actions/*` и помечены `"use server"`: браузер отправляет форму или вызов, а
выполняется код на сервере — там, где есть cookies и ключи Supabase. Наружу возвращаются только
тексты для пользователя: английские ошибки Supabase переводятся на русский.

| Функция | Файл | Что делает |
|---|---|---|
| `signInAction` | `app/actions/auth.ts` | Вход по email и паролю, запись cookies сессии, редирект на `next` или в кабинет; перевод ошибок |
| `signUpAction` | `app/actions/auth.ts` | Проверка полей (имя, email, пароль ≥ 6), **проверка согласия на обработку данных и подтверждения возраста 18+ на сервере**, создание аккаунта (метаданные `name` и `age_confirmed: true`), `emailRedirectTo`; при включённом подтверждении — редирект на `/auth/verify-email`, иначе сразу вход |
| `resendVerificationAction` | `app/actions/auth.ts` | Повторная отправка письма подтверждения; ответ нейтральный (без раскрытия существования адреса), отдельное сообщение при лимите отправок |
| `resetPasswordAction` | `app/actions/auth.ts` | Письмо для сброса пароля с `redirectTo` на `/auth/reset-password`; ответ нейтральный, отдельное сообщение при лимите отправок |
| `confirmSessionFromTokens` | `app/actions/confirm-session.ts` | Завершает вход по токенам из фрагмента адреса (`#access_token=…`) — вариант для шаблона письма Supabase по умолчанию |
| `completeLesson` | `app/actions/complete-lesson.ts` | Отмечает урок пройденным: `upsert` в `lesson_progress` по (user_id, course_type, lesson_id). Идемпотентно; значения из браузера проверяются (`courseType` только `basic`/`confident`/`pro`) |
| `completeModuleTest` | `app/actions/complete-module-test.ts` | Принимает результат теста, повторно проверяет порог сдачи (5 в бесплатном курсе, 7 в платных), пишет **только сданный** тест (`basic-test` / `confident-test` / `pro-test`) |

Типы результатов описаны рядом с функциями (`CompleteLessonResult`, `CompleteModuleTestResult`,
`ConfirmSessionResult`), состояние формы авторизации — `app/actions/auth-state.ts`
(`AuthFormState`: `error`, `info`, введённые значения без пароля).

## 9. База данных (Supabase)

Self-hosted Supabase на сервере в РФ: используются только Auth и Postgres. Таблиц три, все с
включённым RLS.

| Таблица | Колонки | Назначение |
|---|---|---|
| `profiles` | `id uuid` (= `auth.users.id`), `email`, `name`, `created_at` | Имя и почта для кабинета |
| `lesson_progress` | `id uuid`, `user_id uuid`, `lesson_id integer`, `course_type text not null default 'basic'`, `completed_at` | Прогресс уроков и результаты тестов |
| `subscriptions` | `id uuid`, `user_id uuid`, `status text`, `trial_ends_at`, `created_at`, `updated_at` | Доступ к продвинутому курсу |

Как это работает:

- **Политики «только свои строки»**: `auth.uid() = id` для `profiles`, `auth.uid() = user_id` для
  `lesson_progress` и `subscriptions`. Для `subscriptions` есть **только `select`** — менять статус
  может исключительно `service_role`, то есть подписку нельзя выдать себе из браузера.
- **`anon` доступа не имеет** (PostgREST отвечает `401 permission denied`): таблицы читаются только
  вошедшим пользователем или сервисной ролью. Гранты выданы ролям `authenticated` и `service_role`.
- **Уникальный индекс** `(user_id, course_type, lesson_id)` — на него опирается `upsert` в
  `completeLesson`. Старый ключ `(user_id, lesson_id)` снят: урок №1 есть и в базовом, и в
  продвинутом курсе.
- **Значения `course_type`**: `basic` — уроки базового курса (1…8), `basic-test` — тесты его
  модулей (по `lesson_id` 1…2), `confident` — уроки уровня «Уверенный» (1…12), `confident-test` —
  его тесты (по `lesson_id` 1…3), `engineer` — уроки уровня «Инженер» (1…10), `engineer-test` —
  его тесты (по `lesson_id` 1…2), `pro` — уроки продвинутого (1…109), `pro-test` — его тесты (по
  `lesson_id` = `module_order`, 1…26).
- **Ограничение `course_type`**: `lesson_progress_course_type_check` допускает все восемь значений —
  `basic`, `pro`, `confident`, `engineer`, `basic-test`, `pro-test`, `confident-test`,
  `engineer-test`. В живой базе оно одно

## 10. Сборка и деплой

Приложение живёт на **Amvera Cloud** (node 22, `amvera.yml`):

- `build.additionalCommands`: `npm run build:amvera` — `clean` + `ensure:tsconfig` +
  `check:imports` + `npm ci --include=dev --include=optional --no-audit --no-fund` +
  `next build --turbopack`;
- `run`: `node_modules/next/dist/bin/next start`, порт 3000.

Почему сборка устроена именно так (каждый шаг появился из-за реальной поломки на хостинге):

- `ensure:tsconfig` — восстанавливает `tsconfig.json` с алиасом `@/*`, если файл не доехал в
  сборочное дерево;
- `check:imports` — сверяет импорты с именами файлов на диске **с учётом регистра**: Linux регистр
  различает, Windows — нет, поэтому локально всё собиралось, а на Amvera падало «module not found»;
- `.npmrc` → `include=optional` — гарантирует установку `@tailwindcss/oxide-linux-x64-gnu`
  (Tailwind 4 ставит нативный бинарник как optional-зависимость, а сборка идёт с `--omit=optional`);
- `--include=dev` — сборке нужны `typescript` и `tailwindcss`, которые лежат в devDependencies.

Перед деплоем прогоняются: `npm run lint`, `npx tsc --noEmit -p tsconfig.json`,
`npm run check:imports`, `npm run check:docs`, `npm run build`. Проверка сводки в
`build:amvera` намеренно не входит: расхождение в документации не должно останавливать выкладку
работающего сайта. **Автотестов и CI в проекте нет** — см. раздел 12.

Переменные окружения на хостинге: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY` (пока не используется в коде), `NEXT_PUBLIC_SITE_URL`.

## 11. Безопасность и защита данных

- **Пароли и сессии — целиком на Supabase Auth**: пароли хранятся хешами (bcrypt), сессия — в
  httpOnly-cookie, приложение никогда не пишет в `auth.users` и не хранит паролей.
- **Клиентского Supabase в браузере почти нет**: запросы к базе идут только с сервера (Server
  Components, Server Actions), поэтому anon-ключ не используется для чтения данных и токены сессии
  не попадают в бандл. Исключения — страницы `/auth/confirm` и `/auth/reset-password`: сессию там
  после клика записывает браузерный клиент (`lib/supabase/client.ts`), в бандле оказались только
  публичный anon-ключ и одноразовый токен из адреса.
- **RLS + отсутствие грантов у `anon`**: без входа таблицы недоступны, вошедший видит только свои
  строки. Статус подписки меняет только `service_role` — выдать себе Pro через API нельзя.
- **Заголовок `x-supabase-user`** всегда удаляется и заново подставляется middleware, поэтому
  подделать личность через заголовок нельзя (в нём нет токенов — только id, email, имя).
- **Защита от открытого редиректа**: `resolveAfterAuthPath` пускает только внутренние пути, поэтому
  `?next=//evil.com` никуда не уведёт. На странице `/auth/confirm` `next` проверен той же функцией,
  а `type` и токен подтверждает Supabase: чужой или неизвестный тип проверку не пройдёт.
- **Серверная валидация входов**: Server Actions проверяют всё, что приходит из браузера (номер
  урока, тип курса, длина пароля, наличие согласия на обработку данных, подтверждение возраста
  18+) — форма считается недоверенным источником.
- **Доступ к платному контенту решается на сервере**: страницы продвинутого курса отдают только
  2 блока превью, остальное не попадает в HTTP-ответ.
- **Персональные данные**: собирается минимум (имя, email, прогресс), обработка описана в пяти
  документах, приложение и база развёрнуты на серверах в РФ, данные за пределы РФ не выходят.
