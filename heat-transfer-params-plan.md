## 1. Что умеет `rasterToContourSvg`

Функция живёт в `components/constructor/ParameterPanel.tsx:748` (не в
`lib/constructor/`) и объявлена как
`async function rasterToContourSvg(file: File): Promise<string>`.

### Вход

- Ровно `File` — ни `ImageData`, ни URL, ни `HTMLImageElement` снаружи не
  принимаются.
- Внутри: `readFileAsDataUrl` (690) → `FileReader.readAsDataURL` →
  `loadImage` (710) → `<img>` c `image.onload`. `createImageBitmap`
  используется только у литофана (`compressLithophaneImage`, 595).
- Кадр приводится к **центральному квадрату**: `size = Math.min(naturalWidth,
  naturalHeight)` (751) и `drawImage` с обрезкой по центру (767–778). То есть
  широкий логотип 3:1 теряет боковины ещё до всякой трассировки.
- Разрешение растра фиксировано: `CONTOUR_GRID_SIZE = 96` (660), сетка
  96 × 96, масштабирование с `imageSmoothingEnabled` по умолчанию (у литофана
  сглаживание включают явно — 614–615).

### Выход

- Одна строка SVG: `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 96 96">`
  плюс конкатенация `<rect>` (821).
- `<rect>` порождаются построчным run-length: для каждой строки `y` ищутся
  непрерывные отрезки «чернильных» пикселей, каждый отрезок — прямоугольник
  `<rect x="…" y="y" width="…" height="1"/>` (800–805). Других элементов нет:
  ни `<path>`, ни `<polygon>`, ни `<g>`.
- Лимит числа прямоугольников — `CONTOUR_MAX_RECTS = 2400` (669); при
  превышении выбрасывается ошибка «Слишком сложная картинка» (815–819).
- Пустой растр (нет ни одного отрезка) — тоже ошибка: «нужен тёмный силуэт на
  светлом фоне» (809–813).
- Возвращается именно **заливка**, не обводка: каждый `<rect>` — замкнутый
  прямоугольный контур площади (`parseSvgOutline` ветка `rect`, 636–657),
  который затем выдавливается как тело. Атрибутов `stroke`, `fill`,
  `stroke-width` в разметке нет вообще.

### Контур или заливка

- Заливка (`fill`-геометрия). Понятия «линия» в результате нет; «контуром» в
  комментарии (739–747) назван силуэт целиком.
- Побочное следствие для чтения результата: если пользователь откроет такой SVG
  в редакторе, он увидит не путь, а тысячи единичных прямоугольников.

### Внутренние отверстия (буква «О»)

- У растра нет понятия «hole»: внутренность «О» — это просто не залитые
  пиксели. В SVG попадают два вертикальных набора полос с зазором между ними
  (внешняя и внутренняя стенки кольца), иерархии «внешний контур + отверстие» в
  разметке нет.
- Иерархию восстанавливает уже геометрия: `groupContours`
  (`keychain-geometry.ts:258`) считает `depth` по чётности пересечений первой
  точки контура с остальными (`isPointInsideOutline`, 271), контуры с нечётной
  глубиной уходят в `group.holes` (303), затем `createHolePath` → `shape.holes`
  (364). Но полосы кольца друг в друга не вложены — для них `groupContours`
  вернёт несколько независимых групп, то есть «О» станет набором островов с
  зазором, а не телом с отверстием.
- Правила `fill-rule` (`evenodd` / `nonzero`) не реализованы: `parseSvgOutline`
  не читает ни `fill-rule`, ни направление обхода как признак отверстия —
  направление только измеряется `outlineArea` (695) и используется косвенно,
  через геометрическую вложенность.

### Threshold

`isContourPixel` (722–737) — два условия сразу, логическое И:

1. `alpha >= 128` — полупрозрачные и прозрачные пиксели не печатаются;
2. воспринимаемая яркость `0.299·R + 0.587·G + 0.114·B < 200` — непрозрачный
   белый и очень светлый фон тоже не печатается.

То есть порог и по альфе, и по яркости: прозрачный чёрный — пусто (альфа),
непрозрачный белый — пусто (яркость). Всё, что посередине (серое, цветное,
непрозрачное), считается пластиком.

## 2. Поля `HeatTransferParams` и лимиты

Форма записи — как у остальных моделей: тип `HeatTransferParams`,
`DEFAULT_HEAT_TRANSFER_PARAMS`, `normalizeHeatTransferParams`,
`heatTransferStlFileName`, запись в `MODEL_TYPES` / `MODEL_TYPE_LABELS` /
`CONSTRUCTOR_TOOLS` / `ConstructorParams` / `DEFAULT_CONSTRUCTOR_PARAMS`
(перечень мест уже зафиксирован в аудите).

### Обязательные поля

| Поле | Тип | Смысл и почему именно так |
| --- | --- | --- |
| `heatTransferSvg` | `string` | Печатная разметка: замкнутые контуры в координатах `viewBox` исходника. Хранится строкой, как `customSvgData` у брелока (`params.ts:2361`), с тем же лимитом `KEYCHAIN_SVG_MAX_LENGTH = 200_000` (419) и теми же гардами `isCustomSvgData` (2033) / `hasDrawableSvgData` (2042). В поле попадает либо текст пользовательского SVG-файла, либо результат растеризации PNG — но **не** полосы из `rasterToContourSvg` (см. п. 1 и п. 5): нужен вариант с замкнутыми контурами. |
| `heatTransferWidth` | `number` | Ширина готового принта по X, мм. Это габарит детали, а не масштаб SVG: масштаб выводится из bbox контуров при построении (как `transformContours`, 218–220). |
| `heatTransferHeight` | `number` | Высота по Y, мм. При загрузке файла вычисляется из пропорций bbox: `height = width × spanY / spanX`, дальше пользователь правит вручную. Оба размера независимы, как `width`/`length` у брелока, но у брелока контур вписывается с сохранением пропорций и при несовпадении остаётся пустое место (220); для принта это неудобно — масштабировать нужно по осям независимо. |
| `heatTransferLayers` | `number` | Целое число слоёв 1–4. Толщина = `layers × 0.2` мм. Почему слоями, а не мм: 0.2 мм — стандартная высота слоя, пользователю проще выбрать «2 слоя», а не «0.4 мм»; верхняя граница 4 слоя = 0.8 мм, дальше пластина перестаёт гнуться и привариваться утюгом. Шаг толщины 0.2 мм уже принят у нашивки (`CONSTRUCTOR_LIMITS.patchThickness`, 155). |
| `heatTransferMirror` | `boolean` | Зеркалирование по X: принт переносится на ткань лицом вниз, и без зеркала надписи читаются наоборот. Принимается только настоящим `boolean`, как `patchBorder` (2633). |

### Кандидаты, которые в минимальный набор не входят

- `heatTransferThreshold` / режим порога (альфа ↔ яркость) — нужен только если
  допускать JPG и белый логотип одновременно; на первом шаге достаточно
  определять режим по содержимому файла (п. 3.2).
- `heatTransferSimplify` (уровень упрощения) — выводится из габарита
  автоматически: при 200 мм шаг точек 0.1 мм уже не виден, ручной выбор ничего
  не улучшает.
- `heatTransferOutline` (печатать только обводку логотипа) — это уже другая
  модель (тонкая линия), а не heat-transfer.

### Лимиты в `CONSTRUCTOR_LIMITS`

По образцу плоских деталей (`patchSize`, 153; `lithophaneWidth/Height`, 118–125):

```
heatTransferWidth:  { min: 20, max: 200, step: 5, defaultValue: 100, decimals: 0 }
heatTransferHeight: { min: 20, max: 200, step: 5, defaultValue: 100, decimals: 0 }
heatTransferLayers: { min: 1,  max: 4,   step: 1, defaultValue: 2,   decimals: 0 }
```

Обоснование максимума 200 мм:

- стол Ender 3 — 220 × 220 мм, самый узкий из типичных домашних принтеров;
  200 мм оставляет по 10 мм на сторону под юбку/брим и зажимы;
- ровно этот максимум уже стоит у литофана (`lithophaneWidth`/`lithophaneHeight`,
  118–125) с прямым объяснением в комментарии (67–68): панель 200 × 200 вместе с
  рамкой влезает на стол 220 × 220. Для heat-transfer рамки нет, но запас нужен
  тот же;
- ширина листа A4 — 210 мм, то есть 200 мм — самый крупный принт, который ещё
  переносится на стандартную футболку целиком.

Обоснование минимума 20 мм:

- сопло 0.4 мм: элемент тоньше 0.4 мм не пропечатается (у стенок моделей
  минимум 0.8 мм — две линии, `CONSTRUCTOR_LIMITS.wall`, 89);
- при 20 мм и сетке 96 × 96 один пиксель растра равен 0.21 мм — это уже предел
  сопла, мельче силуэт превращается в «кашу» ещё до геометрии (та же логика в
  комментарии литофана, 578–581);
- 20 мм — минимальный размер, который вообще читается на ткани как логотип.

Минимум по самим деталям (элемент < 0.4 мм) лимитом не решается — это правило
фильтрации контуров, см. п. 4.4.

### `normalizeHeatTransferParams`

1. `heatTransferSvg`: если `!isCustomSvgData(value) || !hasDrawableSvgData(value)`
   → `""` (дефолт). Пустая строка — штатное состояние «файл не загружен»:
   модель не активна, кнопка скачивания ведёт себя как у custom-брелока без
   контура (API вернёт 422). Обрезать строку нельзя — обрезанный SVG невалиден,
   отклоняется целиком.
2. Длиннее 200 000 символов → `""`. Лимит считается по `value.length`
   (символы), а не по `file.size` (байты): кириллица в тексте SVG весит больше,
   и в панели это уже учтено (828–835). Отклонять, а не усекать.
3. `heatTransferWidth` / `heatTransferHeight`: `snap(value ?? default, limits)` —
   зажим в `min`/`max` и выравнивание по шагу 5, как `patchSize` (2622–2625).
   `NaN`, `Infinity`, строка → дефолт (поведение `snap`).
4. `heatTransferLayers`: `Math.round(snap(...))` — как `patchStitches` (2637):
   дробное число слоёв бессмысленно.
5. `heatTransferMirror`: `typeof value === "boolean" ? value : default`.
6. Связки полей нет: `width` и `height` независимы, ни один не выводится из
   другого на этапе нормализации — пропорции применяются только при загрузке
   файла в панели. Это отличается от QR-визитки, где габарит выводится из
   `qrCardSize`, и так проще: нормализатор не переписывает введённое значение.
7. Нормализатор не проверяет «есть ли контуры после упрощения»: этим занимается
   пайплайн PNG (п. 3) и API (п. 4.3) — иначе нормализация тянула бы в
   `params.ts` геометрический разбор.

## 3. Обработка PNG: threshold, упрощение, зеркалирование, ограничения

### 3.1. Что загружает пользователь

- PNG (допустимо WebP) с **прозрачным фоном**. Прозрачность — это и есть
  маска печати: всё непрозрачное печатается, всё прозрачное остаётся тканью.
- JPG отклоняется с понятным текстом. Причина не в формате как таком, а в
  физике сжатия: JPEG не хранит альфу и даёт «бахрому» из серых пикселей у
  границы фигуры, а `isContourPixel` считает пластиком всё непрозрачное и
  темнее 200 — то есть серые артефакты попадут в силуэт, и контур выйдет
  рваным. Тот же белый фон JPEG — частая причина «белый логотип пропал» у
  брелока (порог яркости отсекает белое), и для принта это вдвойне обидно,
  потому что печатать его нечем: белого пластика на ткани не видно.
- Дополнительно проверяется, что в файле вообще есть прозрачность (доля
  пикселей с `alpha < 250`): если её почти нет, панель предупреждает «фон не
  прозрачный, проверьте логотип» и переключается на яркостный порог.

### 3.2. Threshold

Основной режим — **альфа**: `alpha >= 128` = пластик, `alpha < 128` = пусто.
Почему не яркость:

- логотип на футболке бывает любым: белым, жёлтым, красным, чёрным. Яркостный
  порог `< 200` (сейчас у брелока, 729–736) съел бы белый и жёлтый логотип
  целиком — на выходе пустой силуэт и непонятная ошибка;
- альфа — это ровно то, что дизайнер нарисовал как «печатается», она не зависит
  от цвета. Полупрозрачные края (antialiasing) делятся пополам порогом 128, что
  даёт ровную границу без «ореола».

Второй режим — **яркость** (`alpha >= 128` и `luminance < 200`, то есть
унаследованный `isContourPixel`) — включается автоматически, когда прозрачности
в файле нет. Это нужно не для «тёмных силуэтов», а для совсем сырых логотипов,
которые пользователь притащил скриншотом: там фон белый и непрозрачный, и другого
сигнала, кроме яркости, нет. Выбора пользователю не даём: `heatTransferMode` в
минимальный набор полей не входит (п. 2), режим определяется по содержимому.

Инверсия (`тёмное = пусто`) не нужна: если пользователь принёс «негатив», он
может инвертировать альфу в редакторе — это один клик, а лишний флаг в
`HeatTransferParams` пришлось бы объяснять в панели.

### 3.3. Упрощение контура

Цель — не 50 000 треугольников из логотипа, а 100–300 вершин на деталь.
Порядок шагов:

1. Растр до рабочей сетки: длинная сторона 512–1024 px (бюджет по памяти и по
   времени, см. 3.5), билинейно, без обрезки до квадрата — в отличие от
   `rasterToContourSvg` (751) пропорции сохраняются целиком.
2. Бинаризация по правилу 3.2 → булева маска.
3. Трассировка границ (marching squares / square tracing) → **замкнутые**
   контуры по границе маски, внешние и внутренние отдельно, с сохранением
   иерархии «кто внутри кого». Полосы `<rect>` здесь не годятся: каждый
   прямоугольник — отдельный контур, и получается до 2400 островов (п. 1).
4. Упрощение **RDP (Douglas–Peucker)** с ε = 0.75 px рабочей сетки.
   Обоснование: 0.75 px после сглаживания — это чуть
   меньше шага печати (0.4 мм сопло при 200 мм принта и 512 px даёт 0.39 мм на
   пиксель), поэтому отброшенные точки всё равно не пропечатались бы. Жёстче
   (ε = 2 px) скругляет углы букв, мягче (ε = 0.2 px) возвращает ступеньки
   растра.
5. Пост-фильтры: убрать почти совпадающие вершины (как `normalizeContour`,
   `svg-outline.ts:48`, с `POINT_EPSILON = 1e-6`), убрать контуры короче трёх
   точек и с нулевой площадью (`parseSvgOutline` уже так делает, 625–631),
   отбросить детали мельче 0.4 мм в готовом масштабе (п. 4.4).
6. Запись результата — `<path d="M … L … Z"/>` (или `polygon`), один элемент на
   контур, `viewBox` = габарит исходника. Никаких `transform`, `stroke`,
   `fill-rule`: разбор их не понимает (п. 5.2).

Бюджет по точкам задаётся существующей константой `MAX_OUTLINE_POINTS = 20000`
(`svg-outline.ts:22`): если после упрощения суммарно больше — либо повторять
RDP с ε × 1.5, либо отклонять файл сообщением «слишком сложный логотип». Второе
честнее: файл на 20 000 точек при 200 мм — это 0.03 мм на точку, то есть шум,
который слайсер всё равно выбросит.

### 3.4. Зеркалирование

Зеркалить **в геометрии**, не в SVG. Причины:

- `parseSvgOutline` не применяет `transform` вообще (`svg-outline.ts:11–12`:
  «Трансформации (`transform="…"`) не применяются»), поэтому
  `transform="scale(-1,1)"` просто потеряется — молча, без ошибки;
- зеркалирование в геометрии уже есть по факту: `transformContours`
  (`keychain-geometry.ts:226–234`) переворачивает Y при переводе в миллиметры,
  туда же добавляется `x → −x` при `heatTransferMirror`. Watertight это не
  ломает: оболочка строится заново из точек, а не отражается матрицей (отражение
  матрицей перевернуло бы нормали — при обратном обходе нормаль смотрит внутрь,
  см. `prism-mesh.ts:11–13`);
- после отражения нужно **развернуть порядок точек** каждого контура, иначе
  `outlineArea` сменит знак, а `groupContours` (`keychain-geometry.ts:258`)
  перепутает внешние контуры с отверстиями.

### 3.5. Ограничения ввода

- Максимальный размер файла — **5 МБ**. PNG 512 × 512 с альфой — это десятки
  килобайт, 4096 × 4096 — единицы мегабайт; 5 МБ покрывает любой нормальный
  логотип и при этом не подвешивает `FileReader`/canvas на слабом ноутбуке.
  Лимит 200 КБ здесь не применим: он про длину SVG-строки, а не про размер
  файла.
- Минимальная сторона — **128 px**, рекомендуемая — 512 px. При 128 px и
  принте 200 мм пиксель равен 1.6 мм: контур получится из десятка вершин, RDP
  съест остальное, и от логотипа останется силуэт-пятно. 512 px — это шаг 0.39
  мм, то есть ровно сопло: мельче рисовать смысла нет. Сообщение при
  недостатке: «картинка мелкая, контур будет грубым».
- Максимальная сторона — **4096 px**. `getImageData` для 4096 × 4096 — это
  64 МБ (4 байта на пиксель) плюс копия при масштабировании; на мобильном
  браузере это уже риск. Литофан обходится сеткой 400 × 400
  (`LITHOPHANE_RESOLUTION`), потому что ему нужна яркость, а не граница; здесь
  сетка 512–1024 px, всё крупнее просто даунскейлится перед трассировкой.
- Пропорции не обрезаются: рабочий растр сохраняет `width / height` исходника
  (в отличие от `rasterToContourSvg`, 751), иначе логотип 3:1 пришёл бы
  квадратом.

## 4. Риски и как их закрыть

### 4.1. Внутренние отверстия («О»)

- Механизм в проекте есть: `createHolePath` (`keychain-geometry.ts:327`) →
  `shape.holes.push` (364), и `ExtrudeGeometry` честно вырезает дырку — так
  сделан и NFC-карман (755–761).
- Проблема не в `ExtrudeGeometry`, а в источнике контуров. `groupContours`
  (258) определяет вложенность геометрически: для каждого контура считается
  `depth` — сколько других контуров содержат его первую точку (271). Контур с
  нечётной глубиной становится `hole` (303), чётной (и нулевой) — `outer` (278).
  Ни `fill-rule`, ни направление обхода для этого не нужны.
- Значит требование к PNG-пайплайну одно: выдавать **замкнутые** контуры границ,
  а не полосы. Тогда «О» придёт как внешний контур + внутренний, `depth`
  посчитается сам, отверстие вырежется. С `rasterToContourSvg` (полосы) это
  невозможно — там каждая полоса самостоятельный прямоугольник, и зазор кольца
  останется зазором между островами.
- Если после упрощения внутренний контур схлопнулся меньше порога (п. 4.4):
  отверстие отбрасывается, буква печатается залитой. Это лучше, чем дырка в
  форме запятой, которая зарастёт при печати.

### 4.2. Несколько островов в одном PNG

- Нового механизма не нужно. `buildShapes` (356) возвращает `Shape[]` — по
  одному на группу, каждая группа выдавливается отдельно `extrudeShape` (690),
  результаты складываются `mergeGeometries` (770). «СНЕГ» тремя словами — это
  три группы, три экструзии, один merge.
- Merge не сваривает оболочки: каждая остаётся watertight сама по себе, а
  слайсер объединяет пересекающиеся тела при печати — тот же принцип заявлен в
  `prism-mesh.ts:4–7` и у всех остальных моделей. Для принта это даже полезнее:
  острова не обязаны пересекаться, они лежат на ткани рядом.
- Ограничение по числу островов всё же нужно: 2400 полос у брелока — предел
  разумного (`CONTOUR_MAX_RECTS`, 669). Для контуров предлагается свой предел:
  не больше 64 групп и не больше 20 000 точек суммарно (`MAX_OUTLINE_POINTS`,
  `svg-outline.ts:22`), иначе файл отклоняется.

### 4.3. Watertight на невыпуклом контуре

- `ExtrudeGeometry` строит замкнутую оболочку и для невыпуклого контура: верх,
  низ и боковая стенка по рёбрам. Ручная обвязка (призматическая полоса по
  контуру) не нужна — брелок с `customSvgData` живёт без неё, и его STL
  принимают слайсеры.
- Опасность не в невыпуклости, а в **самопересечении и вырожденных рёбрах**
  после упрощения: триангулятор (earcut внутри three) на пересекающемся контуре
  выдаёт дыры и нормали вразнобой. Меры:
  - отбрасывать контуры с `|area| == 0` и меньше трёх точек (уже делается,
    625–631);
  - не допускать самопересечений после RDP: при удалении вершины проверять
    локальную ориентацию (`sign` векторного произведения соседей до и после) и
    сохранять вершину, если знак меняется;
  - финальная проверка в API: контуры не пусты, число треугольников > 0. Если
    геометрия пустая — 422 с текстом «контур не построился, упростите логотип»,
    а не пустой STL.
- Отдельный риск — совпадающие вершины у двух соседних островов после
  упрощения (два слова «СНЕГ» касаются). Это не ломает watertight каждой
  оболочки, но может дать z-fighting в предпросмотре; лечится минимальным
  зазором (0.2 мм) при раскладке, если понадобится.

### 4.4. Детали мельче 0.4 мм

- Правило: для каждого внешнего контура после перевода в миллиметры считается
  `min(spanX, spanY)`; если он меньше 0.4 мм (диаметр сопла 0.4), контур
  отбрасывается. Для внутреннего (hole) — тоже, но с обратным смыслом: там
  мелкий контур означает дырку, которую печатать нечем, и её лучше залить.
- Почему отбросить, а не утолщить: утолщение — это морфологическая дилатация
  растра, она склеивает соседние буквы и меняет логотип, а пользователь об этом
  не просил. Отбрасывание предсказуемо и объяснимо.
- Пользователю это сообщается, а не молчит: панель показывает «отброшено N
  мелких деталей (меньше 0.4 мм)», скачивание не блокируется. Тот же тон, что у
  предупреждения о NFC-кармане (`measureKeychainNfc`, 648).
- Если отброшено всё (логотип был из тонких линий) — ошибка загрузки: «логотип
  состоит из линий тоньше 0.4 мм, упростите его или увеличьте размер».

## 5. Открытые вопросы

1. `rasterToContourSvg` (`ParameterPanel.tsx:748`) не переиспользуется: полосы
   `<rect>`, обрезка до центрального квадрата, сетка 96 × 96, предел 2400
   прямоугольников. Для heat-transfer нужен отдельный контурный пайплайн
   (замкнутые пути + иерархия), то есть новая функция в панели, а не правка
   существующей. Это дублирование логики загрузки файла (чтение, проверка типа,
   тексты ошибок) — его стоит вынести в общий хелпер, но это архитектурное
   решение вне этой задачи.
2. `parseSvgOutline` (`svg-outline.ts:593`) не понимает `transform`, `<g>`,
   `<use>`, `fill-rule`, `stroke`, `<text>`. Пользовательский SVG из Figma почти
   всегда с `transform="matrix(…)"` — такой файл разберётся в исходных
   координатах и получится смещённым или перевёрнутым. В брелоке это
   ограничение уже описано в `PROJECT.md`; heat-transfer его унаследует, и в
   панели нужен текст «экспортируйте SVG без трансформаций» — либо отдельная
   задача «применять матрицу при разборе».
3. Вспомогательные функции сборки форм — `transformContours` (185),
   `groupContours` (258), `createShape` (311), `createHolePath` (327),
   `buildShapes` (356) — приватны в `keychain-geometry.ts`. Для heat-transfer их
   придётся либо вынести в общий модуль (условно
   `lib/constructor/svg-shapes.ts`), либо дублировать. Второе дешевле на один
   шаг, но заводит третью копию одной логики — выбор надо сделать до
   реализации геометрии.
4. `ConstructorParams` — плоский объект (аудит, раздел 1), панель и вьюпорт
   перечисляют модели явными условиями с `else`-фолбэком. Добавление
   heat-transfer — правки в 9 местах: `MODEL_TYPES`, `MODEL_TYPE_LABELS`,
   `CONSTRUCTOR_TOOLS`, тип + дефолт + нормализатор + имя файла в `params.ts`,
   `parse*Params` и ветка модели в `route.ts`, `ParameterPanel`, `Viewport`,
   `MODEL_DEFAULT_PARAMS` в `ConstructorClient.tsx`.
5. `heatTransferSvg` до 200 КБ уедет в `saved_projects.params_json`
   (`app/actions/projects.ts:110` пишет `params_json: params`). Явного лимита
   длины на это поле в коде нет — только счётчик проектов
   (`SAVED_PROJECTS_LIMIT`). Нужно до реализации проверить лимит тела запроса
   Next.js/сервера и поведение Supabase при строке такого размера: если
   сохранение обрежет JSON, проект откроется с пустым
   `heatTransferSvg`/`customSvgData`.
6. Толщина хранится слоями (`heatTransferLayers`), а в `CONSTRUCTOR_LIMITS`
   принято хранить миллиметры с `step`. Оба варианта работают: слои удобнее для
   панели и предсказуемы для FDM, мм — единообразнее с `patchThickness`. Решить
   до реализации; при выборе мм формула `Math.round(mm / 0.2)` живёт в
   геометрии, а не в параметрах.
7. Скачивание при пустом `heatTransferSvg`: у брелока API требует непустой
   контур только для `keychainShape === "custom"` (аудит, раздел 2). Для
   heat-transfer контур — единственный источник формы, поэтому пустое поле
   должно давать 422 при любом обращении к API, а не подставлять «запасной
   жетон» наподобие `KEYCHAIN_FALLBACK_SVG`.
