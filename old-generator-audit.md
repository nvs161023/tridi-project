# Аудит старого 3D-генератора по фото

Дата: 16 ноября 2026. Код не менялся: это отчёт о состоянии legacy-потока, а не патч.
Источники: файлы репозитория на коммите `3db1f9d`, git-история 26–27 октября 2026 и
записи в `PROJECT.md` (разделы про Gen API, строки 94–95, 171, 174, 7640–7900).
Живых запросов к gen-api.ru в этом аудите не было — деньги не тратились.

## 0. Резюме

1. **Провайдер — российский агрегатор gen-api.ru** (`https://api.gen-api.ru/api/v1`),
   сеть по умолчанию `trellis-2` (Trellis 2), альтернатива `tripo-3d`. По прайсу
   62,5 ₽ за задачу, фактическое списание в реальном прогоне 26.10.2026 —
   `cost: 75` ₽; поле `is_payment_upfront: true` значит, что **деньги списываются
   при создании задачи, а не при её успехе** (`PROJECT.md`, строки 7782–7784, 7820).
2. **Отсюда «списывались деньги при сбое».** Роут списывал кредит пользователя
   только после успеха (строка 632), но рубли у агрегатора уходили в момент
   `POST /networks/{model}`. Любой сбой после этого — 502/504 — стоил 75 ₽ и не
   возвращался; UI при этом обещал «неудачная генерация — ни одного кредита»
   (`app/3d-generator/page.tsx:171`).
3. **Сбоили обе половины потока, и всё маскировалось одним текстом** «Сервис
   перегружен или не отвечает». Создание задачи: неверное поле картинки
   (`image_urls` вместо `image_url`) и два лишних поля — три причины 422.
   Чтение результата: опрос несуществующего пути `/api/v1/requests/{id}` (404) и
   разбор несуществующего поля `output` вместо `result` (`PROJECT.md` 7780–7834).
4. **Синхронный HTTP-запрос на 4–5 минут.** Роут держал соединение до 270 с при
   `maxDuration = 300`: на сложных фото это 504, задача на стороне агрегатора
   всё равно доходит до конца и оплачена, а `requestId` нигде не сохраняется —
   забрать готовый файл нечем.
5. **Страница была сиротой**: ни одной ссылки на `/3d-generator` в интерфейсе
   нет (единственные упоминания — сама страница и два middleware). Владелец
   мог попасть на неё только по прямому адресу.
6. **Новый поток в Конструкторе** (Tripo/Meshy напрямую, отдельный роут опроса,
   STL после «мясорубки», прогресс-бар) устроен правильнее, но **потерял
   проверки входа и кредитов** на `/api/generate-3d` — это надо вернуть до
   удаления legacy.
7. **Решение:** старую страницу и роут удалить (с 308-редиректом на
   `/constructor`), предварительно перенеся четыре вещи: проверки доступа и
   биллинг, провайдер-модуль, UI-паттерны загрузки фото и терпимый разбор
   ошибок провайдера.

## 2. Разбор по файлам

### 2.1 `app/3d-generator/page.tsx` — страница

- **Что это:** Server Component (`dynamic = "force-dynamic"`, `noindex`) на адресе
  `/3d-generator`. Строки 41–54: `resolveUserId` → редирект гостя на
  `/auth/login?next=%2F3d-generator`, затем `hasActiveSubscription` → замок с
  кнопкой `/courses/pro`, затем `getUserCredits` (только при открытом пакете).
- **Провайдер:** нет, страница только читает базу и рисует интерфейс.
- **Процесс:** доступ → hero «Gen API · Trellis 2» → плашка «Доступно
  генераций: N» → `<GeneratorWorkspace credits>` либо `<LockedGenerator>`
  (строки 136, 148–212).
- **Баги:** текст обещает то, чего код не обеспечивает: «Каждая удачная
  генерация списывает один кредит, а неудачная — ни одного» (строка 171) и
  «Кредиты тратятся только на удачные генерации» (строка 181). Формально это
  правда для нашего счётчика, но не для кошелька платформы: агрегатор брал
  75 ₽ за каждую задачу, включая провалившиеся. Плюс страница-сирота: ни одного
  `href="/3d-generator"` в проекте нет.
- **Что переиспользовать:** сам паттерн «гость → логин с возвратом, без пакета →
  замок с объяснением» уже есть в Мастерской и Конструкторе, дублировать не
  нужно; полезна только идея плашки баланса рядом с заголовком.

### 2.2 `app/3d-generator/GeneratorWorkspace.tsx` — клиентская область

- **Что это:** клиентский компонент: зона drag-and-drop (`label` + скрытый
  `<input type="file" accept="image/*">`, строки 352–388), превью через
  `URL.createObjectURL` с `revokeObjectURL` в `useEffect` (184–196), проверка
  файла `validateImageFile` (57–76), размер `formatFileSize` (79–85).
- **Провайдер:** нет, отправляет `FormData` с полем `file` на `/api/3d/generate`
  (строка 37, запрос — 278).
- **Процесс:** выбрать фото → «Сгенерировать» → `isGenerating` → спиннер
  «Создаем 3D-модель...» (488–505) → при 200 `modelUrl` + `router.refresh()`
  (286–299) → белая ссылка `<a href={modelUrl} download>` «Скачать GLB/STL»
  (521–529). Ответы разобраны по кодам: 403 — кредиты, 502/504 — «Сервис
  перегружен», иначе текст из `error`; сетевой сбой — тот же текст (302–320).
- **Баги:** прогресса нет вообще (только спиннер), время «до 2 минут» занижено
  (реальный прогон — 147 с на простом кубе, сложные фото дольше); 3D-просмотра
  нет, вьювер остался заглушкой (531–546, текст «Вьювер … подключим следом»);
  кнопка блокируется только на время запроса, поэтому после 504 человек жмёт
  ещё раз и запускает **новую оплаченную задачу**; тексты 502/504 скрывают
  настоящую причину. Отмена (`AbortController`) не предусмотрена: закрытие
  вкладки не отменяет задачу и не экономит деньги.
- **Что переиспользовать:** зона drag-and-drop с подсветкой и корректным
  `dragleave` по `relatedTarget` (224–239), `validateImageFile`,
  `formatFileSize`, отзыв object URL, сброс `event.target.value = ""` для
  повторного выбора того же файла (212–221), `role="alert"` для ошибок.

### 2.3 `app/api/3d/generate/route.ts` — синхронный API (главный виновник)

- **Что это:** `runtime = "nodejs"`, `dynamic = "force-dynamic"`,
  `maxDuration = 300` (строки 6–12). Один HTTP-запрос делает всё: загрузку
  фото, создание задачи, ожидание результата, скачивание модели, списание
  кредита.
- **Провайдер:** gen-api.ru. База `https://api.gen-api.ru/api/v1` (15),
  таблица полей `GEN_API_MODELS` (`trellis-2` → `image_url`, `tripo-3d` →
  `image_urls`, 23–26), модель из `GEN_API_MODEL` (147–155), ключ
  `GEN_API_KEY` (393).
- **Процесс (по коду):** 1) ключ и модель, иначе 503 (393–411); 2) сессия
  `supabase.auth.getUser()`, иначе 401 (413–424); 3) `getUserCredits`:
  `null` → 503, `0` → 403 (426–436); 4) `request.formData()`, поле `file`,
  MIME из белого списка (415), пустой файл (400), размер > 10 МБ (413)
  (438–468); 5) `uploadImageToSupabase(file)` в публичный `workshop-temp`,
  получаем public URL (470–484); 6) `POST /networks/{model}` с телом
  `{ image_url }` или `{ image_urls: [url] }`, таймаут 30 с (489–509);
  7) `request_id` из `request_id`/`id` (536–545); 8) цикл `while` с
  `await sleep(3000)` и `GET /request/get/{id}` до 270 с (547–679);
  9) на `success` рекурсивный поиск ссылки (282–287), скачивание в
  `3d-models` с проверкой сигнатуры `glTF`/`{` и лимита 50 МБ (300–365);
  10) `deductCredit` (632); 11) ответ `{ modelUrl, requestId }`.
- **Баги:** см. раздел 4 — именно здесь их концентрация: ожидание модели внутри
  пользовательского запроса, потеря `requestId`, маскировка ошибок 502,
  проверка кредитов без резерва, публичное фото без удаления.
- **Что переиспользовать:** порядок проверок и тексты ошибок (ключ → сессия →
  кредиты → файл), `readBody` — терпимый разбор ответа в текст+JSON (109–123),
  `readValidationMessage` — показ 422 пользователю как 400 (183–211),
  `storeModel` — проверка сигнатуры скачанного файла перед сохранением
  (336–345), `detectImageType` по magic bytes (в `lib/3d/providers.ts:465–499`,
  в новом роуте уже есть свой дубль — 176–206).

### 2.4 `lib/3d/providers.ts` — абстракция провайдеров (не подключена)

- **Что это:** общий интерфейс `GenerationProvider` с тремя методами
  `submit(imageBuffer, options) → { taskId }`, `poll(taskId) →
  pending|success|failed`, `download(modelUrl) → Buffer` (45–63) и реализация
  `Tripo3DProvider` для v3 REST (`https://openapi.tripo3d.ai/v3`, 66).
- **Провайдер:** Tripo3D v3 напрямую, ключ `TRIPO3D_API_KEY` (136) — **другой**
  ключ, чем `TRIPO_API_KEY` нового роута: историческая путаница, которая видна
  и в `.env.example` (строки 67–81).
- **Процесс:** `submit` проверяет сигнатуру изображения (145–159), загружает
  файл multipart-полем в `/files`, получает `file_token`, чистит `input`,
  `file`, `file_token`, `url`, `model_version` из options и создаёт задачу
  `POST /generation/image-to-model` (167–210). `poll` читает `GET /tasks/{id}`,
  `success` → ссылка из `output.model_url` и запасных полей, `failed` /
  `cancelled` / `banned` / `expired` / `unknown` → `failed` с `error_message`
  (214–257). `download` принимает только `https`, не отправляет ключ на
  подписанный URL, отклоняет HTML/JSON и файлы > 50 МБ (259–…).
- **Баги:** нигде не импортируется (`git grep '3d/providers'` пуст) — 574 строки
  мёртвого кода, которые поддерживают иллюзию, что роут умеет переключать
  провайдеров. Роут всё это время ходил только в Gen API.
- **Что переиспользовать:** это самый полезный кусок legacy. Новый
  `/api/generate-3d` повторяет ту же логику вручную: `detectImageType`
  (176–206), `uploadTripoImage` (361), `createTripoImageTask` (405),
  `createTripoMultiviewTask` (438), `createMeshyTask` (476),
  `ProviderError` (92). Логично вынести провайдеров в один модуль по образцу
  `GenerationProvider`, а не держать две копии проверок и парсинга ошибок.

### 2.5 `lib/credits.ts`, `supabase/user_credits.sql`, `lib/storage.ts`

- **Что это:** `user_credits` — таблица «одна строка на пользователя»;
  `getUserCredits` возвращает `null` при недоступном счётчике (30–65),
  `deductCredit` списывает CAS-циклом «обнови строку, если `credits` всё ещё
  равно прочитанному», максимум 3 попытки (80–…). `lib/storage.ts` держит три
  бакета: `workshop-temp` (публичный, фото для агрегатора),
  `3d-models` (публичный, GLB), `workshop-gcode` (Мастерская) (22–28).
- **Провайдер:** не относится к провайдерам генерации.
- **Процесс:** проверка перед генерацией → списание после сохранения модели в
  Storage → `router.refresh()` на клиенте перечитывает баланс.
- **Баги:** проверка `credits <= 0` и списание разнесены во времени — при одном
  кредите три параллельные вкладки проходят проверку и запускают три
  оплаченные задачи, спишется один кредит (TOCTOU). `uploadImageToSupabase`
  не удаляет фото: в `lib/storage.ts` прямо написано «Отдельного удаления здесь
  нет… чистку делает администратор базы» (12–14), то есть фото пользователей
  лежат в публичном бакете бессрочно. Сбой `deductCredit` только логируется
  (632–639) — генерация отдана бесплатно.
- **Что переиспользовать:** сам `lib/credits.ts` (он корректен для «списать
  после успеха») и идею «сначала результат у нас — потом списание». Для нового
  потока нужен ещё резерв (hold) перед созданием задачи, иначе TOCTOU
  повторяется.

## 3. Сравнение: старый поток vs новый

| Критерий | Старая версия (`/3d-generator` + `/api/3d/generate`) | Новая версия (секция в Конструкторе) |
| --- | --- | --- |
| Точка входа | Отдельная страница, ссылок из UI нет (сирота) | Секция «Генератор по фото» в конце `ParameterPanel` конструктора |
| Доступ | Логин + активная подписка «Всё включено», иначе замок | Логин (middleware `/constructor`), пакет не требуется |
| Провайдер | gen-api.ru (агрегатор), `trellis-2` / `tripo-3d` | Tripo3D v3 напрямую (`multiview-to-model`, `image-to-model`) и Meshy (`image-to-3d`) |
| Оплата | `is_payment_upfront: true`: списание при создании задачи, 62,5 ₽ по прайсу, 75 ₽ фактически | Прямые кредиты провайдера; сейчас в коде **нет** ни проверки, ни списания кредитов |
| Транспорт | `multipart/form-data`, поле `file` | JSON `{ images: string[], quality }`, base64 без префикса data URL |
| Ожидание результата | Внутри одного HTTP-запроса: `while` + `sleep(3 с)` до 270 с, `maxDuration = 300` | `POST` только создаёт задачу (`maxDuration = 120`) и сразу отдаёт `{ taskId }` |
| Опрос статуса | Внутри того же запроса, путь `/request/get/{id}` | Отдельный `GET /api/check-3d-status?taskId&service`, клиент опрашивает каждые 3 с цепочкой `setTimeout` |
| Прогресс | Спиннер + «до 2 минут», без процентов | `role="progressbar"`, `aria-valuenow`, проценты из провайдера, три подписи стадии |
| Фото на входе | 1 файл, JPEG/PNG/WebP ≤ 10 МБ, без сжатия | 1–4 фото, сжатие в браузере до 1600 px JPEG 0.9 поверх белой подложки |
| Результат | GLB с текстурой, только скачивание | STL: сварка вершин, `dedup`/`prune`, децимация до ~100 000 треугольников, масштаб 120 мм по максимальному габариту |
| Просмотр | Заглушка «вьювер подключим следом» | `GeneratedModelViewer`: R3F, `STLLoader`, камера и свет по bounding sphere, `OrbitControls` |
| Хранение результата | Публичный бакет `3d-models`, постоянный URL | Временная папка ОС `<tmp>/tridi-3d`, имя = SHA-256 от ссылки на GLB, отдача через `/api/generated-stl/[file]` |
| Хранение фото | Публичный `workshop-temp`, бессрочно, без удаления | Не сохраняется: base64 уходит в теле запроса |
| Ошибки | Почти всё → 502 «Сервис перегружен»; 504 по бюджету; 422 → 400 | `ProviderError` с кодом и текстом, 503 без ключа, 502 на отказ сети, `failed` от задачи отдельно, `role="alert"` |
| Постобработка | Проверка сигнатуры `glTF`, лимит 50 МБ | `processGeneratedMesh`, `MeshFixerError` → 502 с понятным текстом |
| Проверки входа в API | 401 гость, 403 без кредитов, 503 при сбое счётчика | **Нет**: `/api/generate-3d` и `/api/check-3d-status` не проверяют сессию и кредиты |
| Повторные попытки | Каждый клик = новая оплаченная задача; `requestId` не сохраняется | Задача создаётся один раз на отправку; при ошибке клиент показывает причину, но идемпотентности по-прежнему нет |
| Мёртвый код | `lib/3d/providers.ts` (574 строки) не используется | — |

**Главное различие по деньгам.** Старая схема платила агрегатору за факт
создания задачи и не могла вернуть деньги при сбое: любой 502/504 после
`POST /networks/{model}` — это −75 ₽. Новая схема тоже платит провайдеру вперёд,
но: (а) задача создаётся отдельным коротким запросом, (б) статус опрашивается
отдельно и переживает закрытие страницы, (в) результат сразу превращается в
STL, который не нужно ремонтировать. Убыток возможен только если задача
создана и провайдер её провалил — это ответственность провайдера, а не наша
архитектура.

## 4. Баги старой версии

Формат: **что → где → почему → чем это стоило → как в новой версии**.
Приоритет P0 — деньги и потеря результата, P1 — качество и биллинг, P2 — гигиена.

### 4.1 Почему списывались деньги при ошибке (P0)

**B1. Оплата вперёд, а не по результату.** `app/api/3d/generate/route.ts:489`
создаёт задачу `POST /networks/{model}`; `GET /api/v1/networks` отдаёт
`is_payment_upfront: true` (`PROJECT.md:7783`), реальный прогон показал
`cost: 75` ₽ (`PROJECT.md:7820`). Агрегатор списывает деньги в момент создания
задачи. Любая ошибка **после** этой строки возвращала пользователю 502/504,
кредит пользователя не списывался — но 75 ₽ уже ушли с баланса платформы.
Отсюда прямая связка «генерация прошла со сбоем, деньги списались».
*В новой версии:* тот же риск по природе провайдера, но он сужен: задача
создаётся отдельным коротким запросом, а не в пятиминутном ожидании, поэтому
обрыв соединения уже не «теряет» задачу.

**B2. `requestId` нигде не сохраняется.** Роут держит номер задачи только в
локальной переменной (`route.ts:536–547`) и отдаёт его в ответе лишь при
успехе. На 504 (`route.ts:681–686`) номер теряется: задача на стороне Gen API
доходит до конца, файл лежит в чужом облаке, но забрать его нечем — ни клиент,
ни сервер не знают `request_id`. Повторить запрос = ещё 75 ₽.
*В новой версии:* `taskId` возвращается сразу и живёт на клиенте, поэтому
опрос можно продолжить после перезагрузки страницы.

**B3. Пятиминутное ожидание внутри пользовательского HTTP-запроса.**
`maxDuration = 300` (`route.ts:12`), бюджет ожидания `POLL_BUDGET_MS = 270_000`
(`route.ts:56`), а реальный прогон на простом кубе — 147 с (`PROJECT.md:7820`).
Сложные фото не укладываются: 504 на 270-й секунде, деньги списаны, результата
нет. Дополнительно соединение могут оборвать браузер, прокси или хостинг — задача
всё равно оплачена.
*В новой версии:* создание задачи — отдельный роут с `maxDuration = 120`
(`app/api/generate-3d/route.ts:34`), ожидание — отдельный `check-3d-status`
с `maxDuration = 300` под постобработку (`app/api/check-3d-status/route.ts:38`).

### 4.2 Почему были сбои при генерации (P0)

**B4. Неверное поле картинки.** Роут отправлял `image_urls` (поле `tripo-3d`)
для `trellis-2`, который ждёт `image_url`. Gen API отвечал
`422 {"errors_validation":{"image_url":["Поле image url обязательно."]}}`, а роут
превращал любой не-`ok` в 502 «Сервис перегружен» (`route.ts:530–533`) —
настоящая причина была невидима (`PROJECT.md:7786–7789`). Исправлено таблицей
`GEN_API_MODELS` (`route.ts:23–26`, `buildRequestBody` 166–173).

**B5. Лишние поля запроса.** `callback_url: null` и `texture_size: 512`
отклонялись тем же 422 («ошибочный формат URL», «Значение поля texture size
некорректно»). Это была третья причина 422 (`PROJECT.md:7827–7834`), найдена
только живым прогоном. Исправлено удалением полей из тела.

**B6. Опрос несуществующего пути.** Роут ходил в `/api/v1/requests/{id}`,
а результат читается через `/api/v1/request/get/{id}`: 404 «The route …
could not be found» — уже **после** создания оплаченной задачи
(`PROJECT.md:7790–7792`). Исправлено в `route.ts:555–562`.

**B7. Разбор несуществующего поля результата.** Код искал ссылку в `output`,
а `request/get` отдаёт `result` (массив строк) плюс `full_response`; поля
`output` нет вообще, поэтому даже успешная генерация давала 502 «Gen API не
вернул ссылку на модель» (`PROJECT.md:7793–7795`). Исправлено
`extractModelUrl` (`route.ts:282–287`) с рекурсивным обходом и приоритетом
`.glb`.

**B8. Нет повторов на транзиентные ошибки опроса.** Любая сетевая ошибка или
не-`ok` ответ статуса сразу даёт 502 (`route.ts:554–588`), хотя задача жива и
оплачена. Один моргнувший запрос = потерянный результат.
*В новой версии:* клиент повторяет опрос через 3 с и терпит разовые сетевые
сбои.

**B9. Ошибки маскировались общим текстом.** 401/403/415/422/502/504 в UI
сводились к «Сервис перегружен или не отвечает»
(`GeneratorWorkspace.tsx:307–320`), поэтому ни пользователь, ни владелец не
могли отличить «не то фото» от «мы неправильно составили запрос». Именно это
растянуло диагностику на несколько коммитов `7d201d3`, `e83614b`.
*В новой версии:* `ProviderError` несёт HTTP-код провайдера и текст
(`app/api/generate-3d/route.ts:92–100`), а `errorDetail` вырезает сообщение из
ответа сети (161–170).

### 4.3 Биллинг и кредиты (P1)

**B10. TOCTOU на кредитах.** Проверка `credits <= 0` стоит до генерации
(`route.ts:434–436`), списание — после успеха (`route.ts:632`). Между ними
минуты. При одном кредите три параллельные вкладки проходят проверку и
запускают три оплаченные задачи, а спишется один кредит. Резерва (hold) нет.
*В новой версии:* кредитов вообще нет — ни проверки, ни списания
(`app/api/generate-3d/route.ts:545–672`), то есть проблема не решена, а
отложена и стала шире: платный вызов может сделать любой, у кого есть адрес.

**B11. Кредит не связан с рублями.** Стоимость ответа (`cost: 75`) нигде не
читается и не сверяется с балансом Gen API; лимита задач на пользователя или
сутки нет; учёта расходов нет. При цене 75 ₽ за задачу и «бесплатной неудаче»
для пользователя каждая неудача — прямой убыток платформы.
*Что делать в новой версии:* резервировать кредит до создания задачи,
возвращать при `failed`, писать в лог `service`, `taskId`, `quality`, `cost`.

**B12. Сбой списания только логируется.** `deductCredit` вернул `false` —
модель всё равно отдана (`route.ts:632–639`). Это осознанное решение, но
баланс расходится с реальностью; нет ни метрики, ни повторной попытки позже.

### 4.4 Качество результата и UX (P1)

**B13. GLB вместо печатного STL.** Пользователю отдавался GLB с текстурой
(`route.ts:347–350`, бакет `3d-models`), а страница называла его «моделью для
печати». Ни масштаба в миллиметрах, ни ремонта сетки, ни проверки на
watertight — в слайсере такой файл требует ручной работы. *В новой версии:*
«мясорубка» (`lib/constructor/mesh-fixer.ts`): `weld`, `dedup`, `prune`,
`simplify` до ~100 000 треугольников, масштаб 120 мм по максимальному
габариту, экспорт бинарного STL.

**B14. Одно фото 10 МБ без подготовки.** Провайдер получал исходный файл как
есть: большой PNG, прозрачный фон, портретная ориентация. Прозрачный PNG
генераторы читают как пустой объект. *В новой версии:* сжатие на canvas до
1600 px, JPEG 0.9 поверх белой подложки, до 4 ракурсов
(`components/constructor/PhotoGeneratorSection.tsx`, `preparePhoto`).

**B15. Нет прогресса и заниженное время.** Спиннер с текстом «Обычно это
занимает до 2 минут» (`GeneratorWorkspace.tsx:502–504`) при реальных 147 с на
кубе и больше на сложных фото; процентов нет, стадий нет, отмены нет. Человек
не понимает, жива ли задача, и жмёт «Сгенерировать» повторно.
*В новой версии:* `role="progressbar"`, `aria-valuenow`, три подписи стадии,
10-минутный предел и понятное сообщение об истечении.

**B16. Нет 3D-просмотра.** Вместо вьювера — заглушка с текстом «Вьювер с
поворотом и скачиванием подключим следом за генерацией»
(`GeneratorWorkspace.tsx:539–546`). Проверить модель до скачивания нельзя.
*В новой версии:* `GeneratedModelViewer` на R3F + `OrbitControls`.

### 4.5 Приватность и гигиена (P2)

**B17. Фото пользователей лежат в публичном бакете.** `uploadImageToSupabase`
кладёт файл в `workshop-temp` с публичным URL, а удаления нет вообще:
в `lib/storage.ts:12–14` написано «Отдельного удаления здесь нет… чистку делает
администратор базы». Любой, кто узнал URL, видит фото бессрочно.
*В новой версии:* фото не сохраняются — уходят в теле запроса base64.

**B18. Мёртвый код и два ключа Tripo.** `lib/3d/providers.ts` (574 строки)
никем не импортируется, при этом читает `TRIPO3D_API_KEY`, а рабочий
`/api/generate-3d` — `TRIPO_API_KEY` (`.env.example:67–81`). Легко завести не
тот ключ и решить, что «Tripo не работает».

**B19. Страница-сирота.** `/3d-generator` нет ни в одном меню, карточке или
ссылке (`git grep '3d-generator'` находит только саму страницу и два
middleware), `noindex` и «адрес ниоткуда не анонсирован»
(`app/3d-generator/page.tsx:25–26`). Продукт существовал, но пользователь до
него не доходил.

### 4.6 Что требует подтверждения (гипотезы, не факты)

1. **Расхождение 62,5 ₽ и 75 ₽.** В прайсе 62,5 ₽, в ответе задачи `cost: 75`;
   похоже на наценку/округление агрегатора, но отдельного подтверждения нет.
2. **Доля провалов на стороне сети.** В логах различить `failed` самой
   нейросети и наш 502 сейчас нельзя (единый текст), поэтому неизвестно, какая
   часть сбоев была «плохое фото», а какая — ошибка контракта.
3. **Обрывы на хостинге.** Пятиминутный запрос на проде мог обрываться
   прокси/платформой раньше `maxDuration`; в репозитории следов такой
   диагностики нет.

## 6. Рекомендации

### 6.1 Вердикт: старую страницу удалить, не переписывать

Рекомендуемый вариант — **удалить legacy-поток целиком** и оставить единственный
вход «Генератор по фото» в Конструкторе.

Почему не переписывать страницу на новом API:

- страница ниоткуда не ссылается — трафика у неё нет;
- поток уже есть в Конструкторе: второй вход = второй набор состояний,
  прогресса, ошибок и второй путь для багов;
- старый UI умеет меньше: одно фото, нет вьювера, нет прогресса, нет STL;
- переписывание сохранит 500+ строк и мёртвый `lib/3d/providers.ts`.

Если нужен публичный лендинг «3D по фото», его стоит делать отдельно как
маркетинговую страницу с CTA «Открыть конструктор», а не как второй генератор.

### 6.2 Что сделать в новом потоке ДО удаления старого

1. **P0 — вернуть проверки доступа в API.** `/api/generate-3d` и
   `/api/check-3d-status` сейчас не проверяют сессию и кредиты
   (`app/api/generate-3d/route.ts:545` — сразу разбор тела). Любой, кто знает
   адрес, может жечь ключи Tripo/Meshy. Взять порядок проверок из legacy-роута
   (`app/api/3d/generate/route.ts:413–436`).
2. **P0 — кредиты с резервом.** Подключить `lib/credits.ts`: `reserveCredit`
   перед созданием задачи, `commit` при `success`, `release` при `failed` и на
   502/503. Это закрывает и TOCTOU (B10), и «оплатили, а результата нет» (B1).
3. **P1 — лимит на пользователя.** Например, не больше N задач в сутки и N
   одновременных. В legacy лимита не было вообще.
4. **P1 — вынести провайдеров в общий модуль** по образцу `GenerationProvider`,
   чтобы `generate-3d` и `check-3d-status` не дублировали разбор конвертов
   Tripo (`{ code, data }`) и Meshy (плоский объект).
5. **P1 — логировать стоимость и стадии:** `service`, `quality`, `taskId`,
   `cost` (если провайдер отдаёт), длительность. Иначе следующая история про
   «списали деньги» снова начнётся с нуля.
6. **P2 — чистка временных STL:** `<tmp>/tridi-3d` не чистится (только ОС при
   перезапуске). При деплое на несколько инстансов ссылка `/api/generated-stl/…`
   может не найти файл — это стоит проверить до включения генератора всем
   пользователям.

### 6.3 Чек-лист удаления legacy

Удалить файлы:

- `app/api/3d/generate/route.ts` (и пустую папку `app/api/3d/`);
- `app/3d-generator/page.tsx`, `app/3d-generator/GeneratorWorkspace.tsx`;
- `lib/3d/providers.ts` — после переноса нужного в новый модуль.

Почистить код и конфигурацию:

- `middleware.ts:55` — `"/3d-generator"` из `SESSION_PATH_PREFIXES`;
- `lib/supabase/middleware.ts:32` — `"/3d-generator"` из `PROTECTED_PATH_PREFIXES`;
- `.env.example:63–81` — `GEN_API_KEY`, `GEN_API_MODEL`, `TRIPO3D_API_KEY`
  (оставить `TRIPO_API_KEY`, `MESHY_API_KEY`);
- `lib/storage.ts` — `uploadImageToSupabase` и `uploadModelToSupabase`, если
  после удаления у них не останется потребителей;
- `lib/credits.ts` и `supabase/user_credits.sql` — **не удалять**, если кредиты
  подключаются к новому потоку.

Документация:

- `PROJECT.md`: строки 94–95 (env), 171 (роут), 174 (страница), упоминания
  Gen API в разделе 3.11 и в истории 7640–7900; добавить запись «legacy-поток
  удалён, вход один — конструктор»;
