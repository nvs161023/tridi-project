# Полный аудит проекта TriDi перед коммерческим запуском

**Дата:** 16.11.2026

**Коммит:** `235203b` (`feat(gallery): model categorization, filters, and category selection in generator`)

**Режим:** read-only. Исходный код не изменялся. Проверялись репозиторий, сборка, тесты расчётов и read-only запросы к живой базе Supabase.

**Главный вывод:** функционально проект сильный, но **в текущем виде запускать приём денег нельзя**. Есть обход платного доступа, утечка промокодов, пожизненный Pro у разового пакета и юридические документы, которые не описывают продаваемые товары.

> Это технический и продуктовый аудит, а не юридическое заключение. Пункты по 152-ФЗ, оферте и возвратам должен подтвердить юрист.

## 1. Резюме одной страницей

### Что работает

- Курсы, прогресс, тесты, сертификаты, отзывы, форум, профили, блог и юридические страницы собраны и собираются без ошибок.
- Robokassa-платежи сделаны аккуратно: сумма сверяется с каталогом, подпись ResultURL проверяется через `timingSafeEqual`, `InvId` идемпотентен, покупка пишется в `purchases`.
- Кредиты генераций списываются с CAS-защитой от гонок (`lib/credits.ts`), а порядок списания покрыт тестом `npm run check:credits`.
- RLS в репозитории описана почти для всех таблиц; `purchases`, `subscriptions`, `user_credits`, `token_purchases`, `constructor_downloads` для anon закрыты.
- Сборка, типы, линт, импорты и проверка документов проходят.

### Что блокирует запуск

1. **Платный доступ обходится через Server Actions.** `completeLesson` и `completeModuleTest` не проверяют покупку курса, а второй принимает число правильных ответов от клиента. Можно бесплатно получить сертификат платного уровня и оставить отзыв.
2. **`promo_codes` доступны anon-ключом в живой базе.** Сейчас там одна использованная строка; при выпуске партии для Ozon это риск утечки всех свободных кодов.
3. **Разовый пакет `pro` за 9 900 ₽ даёт пожизненный доступ к Pro-инструментам и пожизненные месячные кредиты генераций.** Это не описано в оферте и убивает смысл подписки 1 486 ₽ / 30 дней.
4. **Оферта не описывает подписку Pro и пакеты токенов**, хотя `/pricing` продаёт их, а кнопка оплаты ссылается на оферту.
5. **Политика ПД не описывает фотографии для 3D-генератора, передачу их в Tripo/Meshy и данные клиентов Мастерской.** Это критично для 152-ФЗ.
6. **Возврат подписки не отзывает доступ:** `refundPurchase` закрывает только `purchases`, а `hasActiveSubscription` продолжает видеть `subscriptions`. В живой базе есть строка `active` с `expires_at = null` — это состояние «Pro навсегда».

## 3. Red Zone: что нельзя выпускать в платный доступ

Приоритеты:

- **P0** — блокер запуска: исправить до первой реальной оплаты.
- **P1** — высокий риск: исправить в первые дни после запуска или закрыть временной мерой.
- **P2** — средний риск: планировать, не блокирует, но накапливает долг.

---
### R1. P0 — платный доступ обходится через `completeLesson` и `completeModuleTest`

**Где:** `app/actions/complete-lesson.ts:30-73`, `app/actions/complete-module-test.ts:33-96`, `app/certificate/[courseId]/page.tsx:257-283`, `components/course/ModuleTest.tsx:103-167`, `lib/course-completion.ts:126-208`.

`completeLesson` принимает от клиента `lessonId` и `courseType`, проверяет только формат (число, одно из пяти значений) и пишет строку в `lesson_progress`. Проверки `hasCourseAccess()` там нет. Любой авторизованный пользователь может вызвать Server Action с `courseType = "confident"`, `"engineer"`, `"profit"` или `"pro"` и номерами уроков, включая платные.

`completeModuleTest` принимает `correct` и `total` от клиента. Сервер проверяет только `isModuleTestPassed(correct, total, 7)`, то есть `correct >= min(7, total)`, и не знает, какие ответы были выбраны. Достаточно отправить `correct = 10`, `total = 10`; при `total = 1` достаточно `correct = 1`.

Сертификат платного уровня проверяет только наличие строк прогресса и сданных тестов. Отдельной проверки покупки курса на странице сертификата нет: `hasCourseAccess(..., "pro")` используется только для подписи «Полный курс», а не как условие выдачи.

**Сценарий:** войти без покупок → вызвать `completeLesson` для всех уроков платного уровня → вызвать `completeModuleTest` с `correct = total` → открыть `/certificate/confident` → получить HMAC-сертификат → оставить отзыв через `app/actions/reviews.ts`, который тоже проверяет только прогресс.

**Влияние:** бесплатные сертификаты, фиктивные отзывы, обесценивание платного продукта и обход гейта «сначала тест, потом следующий модуль».

**Исправление:**

- В `completeLesson` определять допустимые уроки по серверному каталогу, а для платных уровней требовать `hasCourseAccess()` или будущий `requireCourseEntitlement()`.
- В `completeModuleTest` не принимать `correct` от клиента: считать на сервере по ответам или принимать массив ответов и сверять с серверными ключами.
- На странице сертификата требовать действующий доступ к курсу или отдельный сертификат-entitlement.
- В `createCourseReview` требовать тот же доступ.
- Добавить тесты: «без покупки action возвращает 403», «поддельный счёт теста не сохраняется», «сертификат без покупки не создаётся».

**Приёмка:** пользователь без покупки не может создать ни одной строки прогресса платного уровня, ни одного сданного теста и ни одного сертификата; попытки логируются.

### R2. P0 — разовый пакет `pro` даёт пожизненный Pro-инструментарий и пожизненные кредиты

**Где:** `lib/subscription.ts:72-87` (`course_id === "pro"` + `expires_at === null` = навсегда), `lib/subscription.ts:427-431`, `app/api/constructor/stl/route.ts:1782`, `app/api/generate-3d/route.ts:710`, `app/api/profiles/download/route.ts:71`, `app/dashboard/workshop/page.tsx:59`, `data/courses.json` (`pro.price = 9900`, `pro.subscriptionPrice = 1486`), `components/landing/ProBundleCard.tsx:39-65`.

Покупка `pro` — разовый платёж 9 900 ₽ с `expires_at = null`. По текущей модели это одновременно: три платных курса навсегда, библиотека профилей навсегда, безлимитный STL из Конструктора, Мастерская, 3 Standard + 1 Ultra **каждый месяц** без срока и доступ к 3D-генератору.

Подписка `pro-subscription` стоит 1 486 ₽ за 30 дней и даёт только инструменты. Разовый пакет окупает её примерно за 6,7 месяца, после чего инструменты и месячные кредиты бесплатны навсегда. Это не «выгода пакета», а более дешёвый продукт, который каннибализирует подписку.

**Исправление:**

- Остановить продажи `pro` как «всё включено» либо явно ограничить его только курсами и профилями.
- Ввести entitlements: `course.*`, `tools.constructor`, `tools.profiles`, `tools.workshop`, `tools.generator`, `credits.standard`, `credits.ultra`.
- Для уже купленных `pro` сохранить доступ (grandfathering), но не распространять на новые продажи.
- Если нужен «пожизненный Pro» — отдельный продукт с ценой, покрывающей API-затраты, и без бесконечных месячных кредитов.
- Обновить карточку пакета и оферту до фактического состава.

**Приёмка:** новый покупатель `pro` не получает инструменты и кредиты без отдельного entitlement; существующие покупатели не теряют уже оплаченный доступ; в отчёте видно, кто получил legacy-доступ.

### R3. P0 — `promo_codes` читаются anon-ключом в живой базе

**Где:** `supabase/promo_codes.sql:76-88`, `app/api/admin/promo/csv/route.ts`, `lib/subscription.ts:223-236`.

**Подтверждено read-only 16.11.2026:**

- `GET /rest/v1/promo_codes?select=id&limit=5` с **anon**-ключом вернул HTTP 200 и одну строку;
- строка имеет `used_at != null` (сейчас это использованный код, не свободный);
- `GET ...&used_at=is.null` вернул 0 строк;
- `purchases`, `subscriptions`, `user_credits`, `token_purchases`, `constructor_downloads` для anon закрыты (401 или 0 строк).

**Почему P0:** свободных кодов сейчас нет, поэтому конкретная утечка ещё не произошла. Но anon-роль **вообще видит таблицу**. Если политика/гранты живой базы отличаются от репозитория, при выпуске партии Ozon свободные коды могут стать доступны для перебора. Промокод — это фактически деньги: один код = один платный курс.

**Исправление:**

1. Применить точный блок из `supabase/promo_codes.sql`: `enable row level security`, `revoke all from anon, authenticated`, `grant select to authenticated`, политика `used_by = auth.uid()`.
2. Проверить anon: 401/403 или 0 строк, а не 200 с данными.
3. Проверить, что authenticated видит только свои активации.
4. Если в логах/выгрузках были свободные коды — считать их скомпрометированными и перевыпустить.
5. Добавить smoke-тест: anon не читает `promo_codes`, `purchases`, `subscriptions`, `user_credits`, `token_purchases`.

**Приёмка:** anon не получает ни одной строки `promo_codes`; партия не читается никем, кроме service_role.

### R4. P0 — оферта не описывает подписку Pro и пакеты токенов

**Где:** `app/legal/offer/page.tsx:30-114` (только разовые курсы и пакет), `:212-220` («разовая покупка не требует продления»), `:246-254` (доступ «не ограничен»), `:258-287` (возврат только курсов/пакета); `lib/legal.ts:29` (редакция 24.10.2026); `app/pricing/page.tsx:85-150` (подписка 1 486 ₽ / 30 дней); `:154-249` (Standard 500 ₽/10, Ultra 600 ₽/5); `app/actions/payments.ts:46-51` (подтверждение оферты); `app/subscription/PlanButton.tsx:178-198`.

В оферте нет подписки Pro, ручного продления, отсутствия автосписаний, пакетов токенов, их количества/срока/правил списания, возврата для подписки и токенов, разделения «курсы vs инструменты». При этом на главной (`app/page.tsx:1046`) написано «без подписок», а `/pricing` продаёт подписку.

**Влияние:** потребитель может оспорить списание; невозможно корректно объяснить возврат; претензии и chargeback; оферта не соответствует продукту, который принимает деньги.

**Приёмка:** каждому `courseId` соответствует раздел оферты; в чеке и на оплате нет товара, которого нет в документах; реклама не противоречит документам.

### R5. P0 — политика ПД не описывает фото, AI-провайдеров и данные клиентов Мастерской

**Где:** `app/legal/privacy/page.tsx:141-187` (только имя, email, пароль, прогресс, техданные), `:403-465` (третьи лица), `:454` (Google назван единственной трансграничной передачей); `app/legal/consent/page.tsx:53-100`; `app/api/generate-3d/route.ts:304-310, 385-415` (фото уходят в Tripo/Meshy); `app/api/workshop/ocr/route.ts` (накладная уходит в ProxyAPI/OpenAI); `supabase/workshop_clients.sql:39-47` (имя, телефон, email, адрес клиента); `app/actions/orders.ts`, `lib/order-processor.ts` (имена покупателей маркетплейсов).

Пользователь загружает фотографии, которые уходят в иностранные AI-сервисы. Мастерская хранит персональные данные **третьих лиц** — клиентов продавца. Политика и согласие об этом молчат и утверждают, что обрабатываются только имя, email, пароль и прогресс.

**Влияние:** обработка ПД без описанного основания и согласия; трансграничная передача без раскрытия; данные клиентов продавца без договора поручения; штрафы, блокировки и претензии. Особенно критично при одновременном запуске генератора по фото и Мастерской.

**Исправление:** составить полную карту данных (фото, видео, 3D-модели, накладные, клиенты, заказы, API-ключи, переписка); обновить политику и согласие (категории, цели, сроки, получатели, трансграничная передача, удаление); раскрыть Tripo3D, Meshy, ProxyAPI/OpenAI, Resend; для Мастерской определить роль оператора/обработчика и обязанности продавца; настроить удаление и сроки хранения; до обновления документов не продавать генератор и Мастерскую как часть Pro; проверить локализацию данных.

**Приёмка:** каждый поток данных из кода есть в политике; есть отдельное согласие на фото и AI-провайдеров; для данных клиентов Мастерской есть правовое основание и договор.

### R6. P0 — возврат подписки не отзывает доступ

**Где:** `lib/refund.ts:33-39` (`pro-subscription` возвращается), `:64-79` (для него нет прогресса), `:333-347` (обновляется только `purchases.expires_at`); `lib/subscription.ts:266-333` (сначала purchases, затем subscriptions); `app/api/payments/robokassa/result/route.ts:253-297` (ставит `active` и `expires_at`); `scripts/test-refund-guard.ts:416-428` (проверяет только purchases).

`refundPurchase` ставит `purchases.expires_at = now`, но не трогает `subscriptions`. Если есть `active` с будущим `expires_at`, доступ к инструментам остаётся. В живой базе уже есть строка `active` с `expires_at = null`; по `lib/subscription.ts:97-101` это **бессрочный доступ**.

**Влияние:** возвращённый покупатель продолжает пользоваться Pro; администратор видит успешный возврат, но доступ не закрыт; при возврате `pro` остаётся `subscriptions`-доступ; аудита возврата, кроме `console.log`, нет.

**Исправление:** возврат-транзакция (закрыть purchases, отозвать/отменить subscriptions, пометить entitlements, вернуть/списать кредиты); инвариант `active` требует `expires_at > now()`; легаси-бессрочность — явный `legacy_grant`; таблица `refund_audit`; расширить тест проверкой `subscriptions` и `hasActiveSubscription`.

**Приёмка:** после возврата `hasActiveSubscription` и `hasCourseAccess` = false; повторный вебхук не восстанавливает доступ; в аудите есть запись.

### R8. P1 — лимит бесплатных STL в Конструкторе обходится параллельными запросами

**Где:** `app/api/constructor/stl/route.ts:1782-1810` (сначала count), `:2065-2087` (запись после генерации); `lib/constructor/downloads.ts:44-63`.

| `engineer` | 3 990 ₽ | курс «Инженер» навсегда |

| `pro` | 9 900 ₽ | три курса + профили + Конструктор + Мастерская + 3D-генератор + месячные кредиты |
| `pro-subscription` | 1 486 ₽ / 30 дней | профили + Конструктор + Мастерская + 3D-генератор + месячные кредиты |

### 4.2. Как принимается решение о доступе

```
покупка Robokassa
        │
        ▼
purchases (inv_id, user_id, course_id, expires_at)
        │
        ├── hasCourseAccess()  ──► курсы (confident / engineer / profit / pro)
        │
        └── hasActiveSubscription()
                ├── purchases.pro (expires_at = null)          → инструменты навсегда
                ├── purchases.pro-subscription (expires_at)    → инструменты до даты
                └── subscriptions (status = active/trial)      → инструменты до даты
                        │
                        ▼
        Конструктор / Профили / Мастерская / 3D-генератор
```

### 4.3. Где логика разъезжается

1. `pro` одновременно курс и подписка — один товар в двух доменах.
2. `pro-subscription` назван legacy в `lib/subscription.ts:8-10`, но продаётся на `/pricing`.
3. `subscriptions` — и trial, и платная подписка, и ручной комп-доступ.
4. Нет сущности entitlement: доступ вычисляется из `purchases` + `subscriptions` + `promo_codes`, каждый новый товар требует правок в нескольких местах.
5. Нет ledger кредитов: баланс — изменяемые счётчики, истории списаний/возвратов на уровне операции нет.
6. Юридические документы описывают только курсы, а деньги принимаются за три домена.

## 5. План разделения бизнес-логики (business-logic separation plan)

Цель: разделить **обучение**, **Pro-инструменты**, **кредиты генераций** и **данные Мастерской** так, чтобы один товар не открывал другой, а доступ проверялся одной функцией и объяснялся одним документом.

### 5.1. Целевые домены и продукты

| Домен | Продукты | Что даёт | Срок |
|---|---|---|---|
| Обучение | `course.confident`, `course.engineer`, `course.profit` | уроки, тесты, сертификат, отзывы | навсегда |
| Обучение | `bundle.courses` | три курса и сертификаты | навсегда |
| Инструменты | `tools.pro.monthly` | Конструктор, Профили, Мастерская, 3D-генератор, 3+1 кредита в месяц | 30 дней, ручное продление |
| Инструменты | `tools.constructor.lifetime` (опционально) | только Конструктор | навсегда |
| Инструменты | `tools.profiles.lifetime` (опционально) | только Профили | навсегда |
| Кредиты | `credits.standard.10`, `credits.ultra.5` | пополнение баланса | не сгорает |
| Мастерская | `workshop.seat` (опционально) | данные клиентов/заказов/принтеров | по подписке |

Ключевое правило: **`bundle.courses` больше не даёт инструменты**, а `tools.pro.monthly` больше не даёт курсы. Если бизнес хочет «всё включено», это отдельный `all_inclusive.lifetime` с отдельной ценой и явным описанием, а не побочный эффект `pro`.

### 5.2. Целевая модель данных

```sql
create table public.orders (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id),
  provider text not null check (provider in ('robokassa')),
  provider_order_id text not null,
  product_code text not null,
  amount numeric(10,2) not null check (amount > 0),
  status text not null check (status in ('pending','paid','refunded','failed')),
  paid_at timestamptz,
  refunded_at timestamptz,
  created_at timestamptz not null default now(),
  unique (provider, provider_order_id)
);

create table public.entitlements (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  code text not null, -- course.confident, tools.constructor, tools.pro.monthly...
  source_order_id uuid references public.orders(id),
  source text not null check (source in ('purchase','promo','admin','legacy','trial')),
  valid_from timestamptz not null default now(),
  valid_until timestamptz, -- null только для явного lifetime-продукта
  status text not null default 'active' check (status in ('active','revoked','expired')),
  created_at timestamptz not null default now(),
  unique (user_id, code, source_order_id)
);

create table public.credit_ledger (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  kind text not null check (kind in ('standard','ultra')),
  delta integer not null check (delta <> 0),
  reason text not null, -- purchase, generation, refund, admin
  order_id uuid references public.orders(id),
  generation_id uuid,
  created_at timestamptz not null default now()
);
```

`orders` отделяет деньги от доступа; возврат — статус заказа + отзыв entitlements. `entitlements` — единственный источник истины для guard. `credit_ledger` даёт аудит начислений/списаний. `valid_until = null` разрешён только для `lifetime`-продуктов.

### 5.3. Целевые guard-функции

Вместо `hasActiveSubscription()`/`hasCourseAccess()` — серверный модуль `lib/access/entitlements.ts`:

```ts
requireCourse(userId, "confident")        // 403, если нет course.confident
requireTools(userId, "constructor")       // 403, если нет tools.constructor
requireTools(userId, "generator")         // 403, если нет tools.generator
getCreditBalance(userId)                  // из credit_ledger
reserveCredit(userId, "standard")         // атомарно, до провайдера
refundCredit(userId, reservationId)       // идемпотентно
```

Правила: API и Server Actions вызывают только guard; `pro` не является магической строкой; каждый отказ пишется в лог с user id, маршрутом и кодом права; есть тестовая матрица «продукт → права» и «guard → продукты».

---

### 5.4. Как должен работать платёж

1. `createRobokassaPayment` принимает `productCode` (не `courseId`), сверяет цену с серверным каталогом, создаёт `orders(status=pending)`.
2. ResultURL проверяет подпись, находит заказ по `InvId`, проверяет сумму и **не** доверяет `Shp_*` как источнику товара.
3. Одна SQL-функция `fulfill_order` в транзакции: ставит `paid`, создаёт entitlements по `product_code`, пишет `credit_ledger`, продлевает `tools.pro.monthly`; всё идемпотентно по `(provider, provider_order_id)`.
4. Если fulfillment упал — 500, Robokassa повторит; повтор не создаст вторые entitlements.
5. `refund_order`: `orders.status = refunded`, `entitlements.status = revoked`, компенсирующая запись в `credit_ledger` по правилам, запись в `refund_audit`.
6. Продление `tools.pro.monthly` сериализуется по `user_id` и считает новый период от `max(now, current_period_end)`.

### 5.5. План миграции без потери покупателей

**Фаза 0 — стоп-кран:** закрыть R1, R3, R6; временно снять `pro`/`pro-subscription`, если юристы не успевают; не выпускать новые промокоды до фикса RLS; не продавать генератор/Мастерскую, если политика ПД не обновлена.

**Фаза 1 — схема и backfill:** добавить `orders`, `entitlements`, `credit_ledger`, `refund_audit`; перенести `purchases` в `orders`; выдать entitlements: `confident/engineer/profit` → `course.*`, `pro` → `bundle.courses` + `legacy.tools.all` (только уже купленным), `pro-subscription` → `tools.pro.monthly`, токены → `credit_ledger`; `active + null` → явный `legacy.tools.lifetime`.

**Фаза 2 — двойное чтение:** guard читает entitlements, при отсутствии — fallback на старую логику + warning; новые покупки пишут две модели; сравнение результатов в логах.

**Фаза 3 — переключение:** все API/Actions на guard; `hasActiveSubscription` остаётся legacy-адаптером; витрина «курсы / инструменты / токены» раздельная.

**Фаза 4 — очистка:** `purchases.course_id` — историческое поле; удалить продажу `pro`, если lifetime не утверждён; через 90 дней удалить fallback и старые guard.

**Откат:** feature flag `ENTITLEMENTS_MODE=legacy|dual|new`; при инциденте — `legacy` без миграции назад.

### 5.6. Что показать покупателю

- **Курсы:** «Доступ навсегда, без подписки. Сертификат после тестов. Инструменты не входят».
- **Инструменты:** «1 486 ₽ за 30 дней. Конструктор, Профили, Мастерская, 3D-генератор, 3+1 кредита. Продление ручное, автосписаний нет».
- **Токены:** «500 ₽ за 10 Standard, 600 ₽ за 5 Ultra. Не сгорают, не дают доступ к курсам».
- **Всё включено:** только отдельный продукт с отдельной ценой, сроком и офертой.

Убрать с главной «без подписок» в общем контексте; заменить на «курсы — навсегда, инструменты — по подписке или пакетам».
