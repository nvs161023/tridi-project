## 0. Окружение Amvera

Проверить до браузерного прогона: Amvera → проект → «Переменные окружения».

| Переменная | Обязательна | Зачем | Если не задана |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | да | адрес проекта Supabase | `?demo=unavailable` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | да | вход через Supabase Auth | `?demo=unavailable` |
| `DEMO_WORKSHOP_PASSWORD` | да | пароль демо-аккаунта, живёт только на сервере | `?demo=unavailable` |
| `DEMO_WORKSHOP_EMAIL` | нет | почта демо-аккаунта; по умолчанию `demo@tridi-print.ru` | берётся почта по умолчанию |
| `NEXT_PUBLIC_SITE_URL` | желательно | `https://tridi-print.ru` — резервный origin для редиректа | резерв — тот же боевой домен, но лучше задать явно |

Три вещи, на которых чаще всего спотыкаются:

- `DEMO_WORKSHOP_PASSWORD` — не `NEXT_PUBLIC_*`, поэтому в сборку не вшивается,
  но и не подхватывается на лету: после правки нужен перезапуск контейнера.
- Если `DEMO_WORKSHOP_EMAIL` на проде задан, он должен совпадать с почтой
  демо-аккаунта в Supabase (той, что создал `npm run seed:demo`). Иначе маршрут
  логинится под одной почтой, а признаки демо-аккаунта ищутся по другой.
- `SUPABASE_SERVICE_ROLE_KEY` нужен не маршруту демо, а seed-скрипту и
  админским/сертификатным роутам. Seed запускается с локальной машины против
  прод-БД, поэтому ключ нужен локально в `.env.local`, а не в контейнере.

## 1. Проверка без браузера

PowerShell, из любой папки:

```powershell
curl.exe -sS -o NUL -D - "https://tridi-print.ru/api/demo/workshop"
```

Ожидаемый ответ:

```
HTTP/1.1 303 See Other
location: https://tridi-print.ru/dashboard/workshop?demo=1
cache-control: no-store
```

`curl.exe`, а не `curl`: в PowerShell `curl` — это алиас `Invoke-WebRequest`, он
не печатает заголовки так же. Cookies тут не нужны: запрос проверяет только
первый шаг, ответ и есть редирект.

Три возможных исхода:

| `location` | Значение | Куда идти |
| --- | --- | --- |
| `?demo=1` | демо-вход работает | §3 |
| `?demo=unavailable` | не хватает Supabase URL/anon key или пароля демо | §2 |
| `?demo=error` | Supabase отклонил вход под демо-аккаунтом | §4 |

Отдельно посмотреть на сам `location`: он должен вести на публичный домен.
Внутренний адрес вида `http://run-…:3000` браузер не откроет. Маршрут берёт хост
из `x-forwarded-host`, а если прокси его не прислал — падает назад на
`NEXT_PUBLIC_SITE_URL` / боевой домен (`lib/site-url.ts`).

- [ ] `303` и `location` на `https://tridi-print.ru`, а не на `run-…:3000`
- [ ] `cache-control: no-store` — редирект не кэшируется прокси

## 2. Если `?demo=unavailable`

Причина одна из трёх: нет `NEXT_PUBLIC_SUPABASE_URL`, нет
`NEXT_PUBLIC_SUPABASE_ANON_KEY` или пустой `DEMO_WORKSHOP_PASSWORD`
(`app/api/demo/workshop/route.ts`).

**Вариант A — пароль уже есть, но не задан в Amvera.** Вписать
`DEMO_WORKSHOP_PASSWORD` и `DEMO_WORKSHOP_EMAIL` в переменные окружения,
перезапустить контейнер, повторить §1.

**Вариант B — пароля нет нигде.** Запустить seed против прод-БД с локальной
машины:

```powershell
$env:NEXT_PUBLIC_SUPABASE_URL = "https://<project>.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY = "<service_role>"
$env:DEMO_WORKSHOP_EMAIL = "demo@tridi-print.ru"
$env:DEMO_WORKSHOP_PASSWORD = "<придуманный пароль>"
npm run seed:demo
```

Что делает скрипт: находит или создаёт пользователя с `user_metadata.is_demo =
true` и `email_confirm: true`, выдаёт ему активную подписку Pro на год, удаляет
прежние демо-данные и создаёт эталонный набор (клиенты, товары, склад, принтеры,
заказы с позициями и заданиями печати). В конце печатает почту, пароль, `user_id`
и количество строк по таблицам.

Два предупреждения:

- Если `DEMO_WORKSHOP_PASSWORD` не задан вообще, скрипт генерирует пароль,
  печатает его в консоль и дописывает в `.env.local` (файл в `.gitignore`).
  Этот пароль и нужно вписать в Amvera.
- Seed идемпотентен: он удаляет данные демо-аккаунта и создаёт заново. На прод-БД
  это безопасно, потому что аккаунт демонстрационный, но запускать его стоит
  осознанно — данные, которые кто-то успел добавить в демо, исчезнут.

- [ ] `DEMO_WORKSHOP_PASSWORD` непустой в окружении Amvera
- [ ] `DEMO_WORKSHOP_EMAIL` совпадает с почтой демо-аккаунта в Supabase
- [ ] контейнер перезапущен после правки переменных
- [ ] §1 снова даёт `?demo=1`

## 3. Браузерный прогон (инкогнито)

Окно инкогнито — не формальность: демо-вход выдаёт cookies демо-сессии, и в
обычном окне вы потеряете свою. По той же причине не проверять демо под своим
аккаунтом: после нажатия кнопки вы окажетесь демо-пользователем.

1. Открыть `https://tridi-print.ru/tools/workshop`. На витрине две кнопки к
   демо — «Смотреть демо-мастерскую» в первом экране и «Открыть демо» в блоке
   «Демо-доступ без регистрации». Обе ведут на `/api/demo/workshop`.
2. Нажать любую. Ожидаемо: адрес `/dashboard/workshop?demo=1`, сверху плашка
   «Демо-доступ» с заголовком «Смотрите, но не меняйте», текстом про пример
   данных и кнопками «Оформить Pro» и «Выйти из демо».
3. Проверить вкладки: «Заказы», «Склад», «Принтеры», «Товары», «Клиенты»,
   «Калькулятор», «Реквизиты», «Интеграции». В каждой — непустые данные.
4. Отдельно посмотреть «Принтеры»: после демо-входа маршрут обновляет
   `last_seen_at` у принтеров демо-аккаунта, поэтому сразу после входа они не
   должны быть «офлайн». Это косметика: агента фермы в демо нет, и через
   несколько часов без повторного входа карточки могут посереть.
5. Проверить запрет записи в нескольких местах: сохранить клиента, товар,
   катушку на складе, изменить статус заказа. Ожидаемо во всех случаях — текст
   `DEMO_READ_ONLY`: «В демо-мастерской нельзя сохранять изменения: здесь только
   пример данных. Оформите подписку Pro, чтобы вести свои заказы, склад и
   принтеры». Кнопка «Создать заказ» форму открывает, но сохранение вернёт тот же
   текст — это ожидаемое поведение, а не поломка.
6. Обновить страницу (F5): данные прежние, ничего из попыток сохранения не
   применилось.
7. Проверить границы демо-сессии: перейти на `/dashboard`, `/constructor`,
   `/forum/new`, `/my-models`. Ожидаемо — редирект назад в
   `/dashboard/workshop?demo=readonly` (`lib/supabase/middleware.ts`). Публичные
   разделы (`/`, `/pricing`, `/courses/*`) должны открываться как обычному гостю.
8. Нажать «Выйти из демо»: форма уходит `POST /logout`, вы снова гость. Повторное
   нажатие кнопки демо снова открывает мастерскую.
9. Мобильный прогон 390×844: плашка не перекрывает контент, кнопки нажимаются,
   горизонтального скролла нет. Мерить нужно не `documentElement.scrollWidth`, а
   две вещи: `window.innerWidth` на профиле iPhone (`width=device-width`, ожидаем
   390, а не больше) и `window.scrollX` после `window.scrollTo(5000, 0)` (ожидаем

   `innerWidth` 390. После фикса (`[contain:layout]` на скроллерах) обе метрики
   равны 390 — см. §7.4.
10. Консоль браузера: ошибок нет. Предупреждения Supabase о сессии допустимы,
    `pageerror` — нет. Ошибка React #418 на проде — платформенная (T07a в
    `site-improvement-plan.md`), не дефект демо; на быстрой сети её нет, на
    медленной она появляется и на публичных страницах. См. §7.2 и §7.4.

## 4. Если `?demo=error`

Здесь Supabase принял запрос, но отказал во входе. Маршрут пишет причину в лог
контейнера строкой «Демо-вход не выполнен: …» — начать с логов Amvera. Дальше по
порядку:

1. **Пользователь существует?** Supabase → Authentication → Users: почта из
   `DEMO_WORKSHOP_EMAIL` (или `demo@tridi-print.ru`), в метаданных
   `is_demo: true`.
2. **Пароль совпадает?** Проще не гадать, а перезапустить seed с нужным
   `DEMO_WORKSHOP_PASSWORD`: скрипт обновляет пароль существующего пользователя, а
   не только создаёт нового.
3. **Почта подтверждена?** У демо-аккаунта должно быть `email_confirm: true`,
   иначе Supabase не пустит по паролю.
4. **Не сработал ли rate limit?** Несколько прогонов подряд с одного IP могут
   упереться в лимит Supabase Auth; подождать и повторить.
5. После любой правки — перезапуск контейнера и повтор §1.

- [ ] причина из логов прочитана, а не угадана
- [ ] демо-пользователь найден и подтверждён
- [ ] пароль в Supabase и в Amvera — один и тот же
- [ ] §1 даёт `?demo=1`

## 6. Что известно заранее (не блокеры T07)

- **Демо-вход заменяет текущую сессию.** Если вошедший пользователь нажмёт
  «Смотреть демо-мастерскую», cookies станут демо-сессией. Вернуться — только
  обычным входом. Это следствие того, что демо живёт на тех же cookies Supabase;
  если на проде это будет мешать, это отдельная задача, а не поломка T07.
- **Прогресс печати в демо замирает.** Агента фермы у демо-аккаунта нет,
  `last_seen_at` обновляется только на входе.
- **Демо видит только свои данные.** Таблицы мастерской закрыты RLS по
  `auth.uid() = user_id` (см. `supabase/workshop_clients.sql` и соседние
  миграции), поэтому в демо не может появиться чужих заказов. Проверить это
  стоит глазами: имена клиентов должны быть придуманными.
- **Скриншоты на витрине — из этого же аккаунта.** Их пересобирает
  `npm run shots:workshop` при запущенном сервере; после пересоздания демо-данных
  снимки могут разойтись с тем, что видит гость. Не блокер, но если правили
  данные — стоит перегенерировать.

### 7.2. Дефекты прогона

**D1. Мобильная мастерская шире экрана (заказы, клиенты, товары). — исправлен.**
На 390×844 `window.scrollX` после `window.scrollTo(5000, 0)` равен **762**,
`main.left = -762`: страница реально уезжает в пустое поле (скриншот пустой).
На профиле iPhone 13 (`width=device-width`, `initial-scale=1`) браузер расширяет
layout viewport: `window.innerWidth = 1152` вместо 390, то есть мастерская
показывается уменьшенной. Переполнение даёт `[data-kanban-board]` в
`components/workshop/WorkshopOrdersTab.tsx` (строка ~909): если скрыть его через
DevTools, `scrollX` сразу становится 0 и `documentElement.scrollWidth = 390`.
Аналогично «уезжают» «Клиенты» (457) и «Товары» (417) — там таблицы
`min-w-[800px]`/`min-w-[760px]`. Похоже, `overflow-x-auto` у обёртки не
удерживает ширину на мобильном: внутренний скролл есть (`scrollWidth` доски
1124 при `clientWidth` 274), но корневой элемент всё равно растягивается до
содержимого. Нужен фикс в вёрстке (ограничить ширину доски/секции, например
`min-w-0` по цепочке и `overflow-x-clip` на корне страницы) и повторный
мобильный прогон.

**Причина оказалась точнее:** Chromium учитывает внутреннюю ширину
прокручиваемого содержимого в `documentElement.scrollWidth`, даже когда сам
контейнер уже, и мобильный браузер расширяет layout viewport под это число.
`overflow: hidden`/`clip` у обёртки не помогает (проверено), а `contain: layout`
изолирует раскладку: `documentElement.scrollWidth` падает с 1152 до 390, и
внутренний скролл доски продолжает работать (проверено: `scrollLeft = 240`).
Поэтому `[contain:layout]` добавлен к четырём прокручиваемым контейнерам:
доска заказов, таблицы «Товары», «Клиенты» и «Маркетплейсы». Замер после фикса —
§7.4.

**D2. Плавающая ошибка гидратации React #418. — вынесена в T07a.**
`pageerror: Minified React error #418` на `/dashboard/workshop?demo=1`:
3 загрузки из 7 (первый вход + 6 перезагрузок), в т.ч. на `?demo=readonly`.
Что проверено в первом прогоне:

- сравнение текста SSR (JS выключен) с гидратированным DOM — расхождений 0;
- в dev-режиме (в т.ч. с `TZ=UTC`) не воспроизводится;
- `Intl.NumberFormat`/`Intl.DateTimeFormat` в Node и Chromium дают одинаковые
  коды символов (U+00A0), версия ICU не при чём;
- при закрытом WebSocket к Supabase (`page.routeWebSocket`) — 0 ошибок из 7.

Гипотеза «данные успевают обновиться между ответом сервера и гидратацией»
не подтвердилась: при закрытом сокете ошибок не меньше, а больше (6 из 14
против 4 из 14), а сама ошибка возникает **до первых мутаций DOM**. Дальнейшая
диагностика (§7.4) показала, что дефект не связан ни с демо, ни с мастерской:
он воспроизводится на публичной `/tools/workshop`, не зависит от
layout-компонентов и от сборщика, а на статической `/pricing` не появляется.
Это общая проблема гидратации Next 15.5.25 + React 19.1 при стриминге на
медленной сети — отдельная задача `T07a` в `site-improvement-plan.md`.

Сверх того в мастерской убран класс гонок «Realtime-событие пришло, пока React
ещё гидрирует разметку»: `router.refresh()` из подписок «Заказов» и «Принтеров»
теперь ждёт первой паузы главного потока (`lib/workshop/hydration.ts`).
Это не устраняет платформенный остаток, но убирает наше собственное окно.
